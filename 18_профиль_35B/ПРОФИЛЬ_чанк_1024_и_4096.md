## КПД четырёх главных ядер

Считается по **полезной** работе, без набивки.

**`moe_pre_q4_gate_up`.** 40 слоёв × 32768 токенов × 8 экспертов × (1024 выхода × 2048 k × 2) =
**4.398·10¹³ флоп** за префилл. Время 990.71/3 = 330.2 мс →
**133.2 TFLOPS = 51.9% потолка bf16.** С нашей плиткой 2×2 — 312.5 мс → **140.7 TFLOPS = 54.8%**.

**`moe_pre_qx_down`.** 40 × 262 144 × (2048 × 512 × 2) = **2.199·10¹³ флоп**. 183.0 мс →
**120.1 TFLOPS = 46.8%**. С 2×2 — 175.0 мс → **125.7 TFLOPS = 49.0%**.

**`causal_attention_prompt_i8` — здесь потолок не один.** Ядро гибридное:
`QK^T` идёт через `mma_s8` (`m16n8k32.s8`), а `PV` — через `mma_f16`, причём V распаковывается
из int8 упакованной FP16-арифметикой. Половины равны по числу операций:

| половина | флоп (10 слоёв GQA) | потолок | идеальное время |
|---|---:|---:|---:|
| `QK^T`, int8 | 4.398·10¹³ | 1060.7 TOPS | 41.5 мс |
| `PV`, fp16 | 4.398·10¹³ | 256.7 TFLOPS | 171.3 мс |
| | | | **212.8 мс** |

Измерено 489.7 мс → **43.5% смешанного потолка**. И главное здесь не КПД, а состав:
**четыре пятых идеального времени внимания — это половина `PV`, потому что она считает в fp16,
а не в int8.** Ускорять `QK^T` бессмысленно, он и так на быстрых тензорных ядрах.

**`w8_rowsplit_gemm_mma`.** Знаменатель посчитан по `config.h`, а не оценён.

*Слой GQA* (их 10): входная проекция `query_projection_rows = 2 × query_size = 8192` строк плюс
`k` и `v` по `kv_size = 512` — итого 9216 строк из 2048; выходная проекция 4096 → 2048.
Вместе `(9216 + 4096) × 2048 = 27 262 976` весов.

*Слой GDN* (их 30): входная проекция `convolution_dim = 2 × key_dim + value_dim = 8192` строк
плюс выходной гейт `value_dim = 4096` — итого 12 288 строк из 2048; выходная проекция 4096 → 2048.
Вместе `(12 288 + 4096) × 2048 = 33 554 432` веса.

Всего `10 × 27 262 976 + 30 × 33 554 432 = 1 279 262 720` весов ≈ 1.28·10⁹.
Префилл 32768 токенов → `2 × 1.279·10⁹ × 32768 = 8.385·10¹³ флоп`.
Время 1337.83/3 = 445.94 мс → **188.0 TFLOPS = 73.2% потолка bf16.**

Веса при этом читаются раз на чанк: 8 × 1.359 ГБ = 10.9 ГБ за 445.9 мс = 24.4 ГБ/с, то есть
**полоса тут ни при чём, ядро упирается в счёт.**

**Сверка знаменателя с размером артефакта.** Считать веса по конфигу легко ошибиться, поэтому
сумма проверена против того, что движок реально загружает — 21 038 461 952 байта:

| часть | байт |
|---|---:|
| маршрутизируемый MoE, 40 слоёв × 256 экспертов (Q4 gate/up + Q5 down, Q6 у 34/38/39) | 18.55 ГБ |
| плотные проекции W8 (наш знаменатель) | 1.359 ГБ |
| эмбеддинг W8, 248 320 × 2048 | 0.540 ГБ |
| `lm_head` Q6 | 0.397 ГБ |
| черновая голова Q4 | 0.143 ГБ |
| общие эксперты W8, 40 слоёв | 0.134 ГБ |
| **сумма** | **21.12 ГБ** |

Расхождение с загруженными 21.04 ГБ — **0.4%**, и оно объясняется нормами, роутерами и весами MTP,
которых я не считал. Знаменатель для 73.2% сходится с артефактом. Форма плитки у него уже правильная — честная
двумерная сетка варпов `MT × NT`, двойная буферизация фрагментов, программная конвейеризация.
Ось «плитка варпа» там закрыта по построению.

### Причина найдена в коде, и она одна

```cpp
const bool wide_plan   = tokens >= kSparseMoePrefillWideMin;   // = 768
const int route_job_bn = wide_plan ? 64 : 32;
```

Порог задан **в токенах**, а решает **число колонок на эксперта**: `tokens × top-k / эксперты`.
При 8 из 256 это `tokens / 32`.

| чанк | колонок на эксперта | плитка | набивка |
|---|---:|---:|---:|
| 768 (порог) | 24 | 64 | **62%** |
| 1024 | **32** | 64 | **50%** |
| 2048 | 64 | 64 | 0% |
| 4096 | 128 | 64 (две плитки) | 0% |

При чанке 1024 **половина каждой плитки перемножает пустоту.** Это ровно тот множитель, который
виден в замере: полезный КПД `q4_gate_up` падает с 51.9% до **31.6%**, а с учётом набивки
выданная работа остаётся на прежних ~63% — то есть ядро работает так же хорошо, просто половину
времени считает ничто.

Ровная плитка требует `tokens ≥ 64 × 256 / 8 = 2048`.

### Что при этом становится лучше

GDN-тракт при коротком чанке **быстрее**: `gdn::output` −28.4%, `state_passing` −9.1%,
`causal_conv1d_prefill_pairs` −10.3%, `sigmoid_gate_mul` −25.0%. Вместе это ~35 мс против ~1220 мс
потери на MoE и внимании, но знак противоположный и это надо помнить: **единого «лучшего чанка»
для всех ядер нет.**
