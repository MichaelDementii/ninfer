# Ревью первого круга и что по нему сделано

Три независимых агента в чистом контексте, каждый со своим углом: корректность (враждебная),
соответствие правилам репозитория, аудит доказательств. Ниже — что нашли, что исправлено и чем
проверено.

---

## 1. Корректность: дефекта нет, и это показано, а не заявлено

Агент написал свой CUDA-стенд (`/root/scratch_rev1/`), прогнал **старое и новое тело `dequant_w`
бок о бок в одном CTA** по всем **27 реальным инстанциациям** `(BM, BK, THREADS)` — список получен
перебором `W8RowSplitMmaGemmSchedule<...>` по шести Op-семействам, все шесть точек запуска передают
литеральное расписание, так что перечисление полное — и по всем остаткам
`kt % SCALE_CACHE_TILES`, со счётчиками записей на каждый элемент.

**Результат: `As` побитово одинаков во всех случаях, каждый элемент записан ровно один раз.**
Ни пропусков, ни двойных записей. Этим одним прогоном закрыты сразу три заявки: покрытие цикла,
адрес полуслова шкалы и побитовость.

Отдельный сквозной стенд: два бинаря из накладываемых заголовков (не один TU — это была бы ловушка
ODR), 12 конфигураций, включая `Full=false`, рваные `M`/`N`, `padded_k > k`, все шесть расписаний
плюс `BK=128`. **Все 12 отпечатков выхода совпали бит в бит.**
`compute-sanitizer` memcheck / racecheck / synccheck — ноль ошибок и ноль гонок; девять остаточных
memcheck-сообщений — предсуществующие в нетронутом `stage_x` и одинаковы на обеих руках.

Проверено и чисто также: выравнивание `uint2`-чтения (8 Б) и `int4`-записи (16 Б) для всех
достижимых `(row, BK, col)`; порядок восьми элементов внутри 16-байтовой записи; сходимость варпа
для убранных шаффлов; отсутствие WAR-гонки по `As` через барьер; `kSwiGlu`-переразметка строк
(её в тронутом коде нет).

## 2. Две правки в коде, которые он предложил, — обе приняты

**`static_assert` был декоративным.** Показано на стенде, а не рассуждением:
`CodesPerChunk = 16` проходит `32 % 16 == 0`, но `w8g32_swz64` переставляет **восьмиэлементные**
пробеги — при `row & 7 == 1` колонки 0..15 ложатся как `8..15, 0..7`, и 32-байтовая запись положила
бы коды не туда. `CodesPerChunk = 4` тоже проходит ассерт, а `col = chunk * 8` не сжимается, и
`uint2` уезжает за границу `Cr`. То есть константа читалась как настраиваемая и ею не была: тело
жёстко зашивает восьмёрку в `uint2`, в `decoded[4]`, в `pair < 4` и в `int4`.

Константа убрана. Осталось `kChunksPerRow = BK / 8`, в комментарии — обе настоящие причины, почему
восемь (гранулярность свизла и делимость 32-кодовой группы), и ассертится `BK % 8 == 0` — то, что
действительно может упасть при смене плитки.

**Файл уже владеет нужным типом.** В том же заголовке лежит
`union alignas(16) W8Bf16x8Bits { uint4 raw; __nv_bfloat162 pair[4]; }`, созданный ровно для этой
формы и уже используемый в residual-эпилоге. Код собирал то же самое руками через `unsigned[4]`,
два `reinterpret_cast` и `make_int4`. Переписано на union.

**Проверка, что правки не изменили генерируемый код.** Пересборка, затем `cuobjdump -sass` на обоих
бинарях:

```
sizes: 12 415 154 строк в обоих дампах
differing lines: 76 — и все 76 это строки `Function :`, где сменился per-compilation module id
                 (..._1515774_ -> ..._1548942_) у 38 инстанциаций с internal linkage
function bodies whose instruction text differs: 0   (из 2893 сопоставимых)
registers / shared / spills: идентичны
```

То есть переработка — чистая замена выражения: **device-код байт в байт тот же.** Тем не менее
кампания перезапущена целиком на ветке с правками, чтобы каждое число в заявке было снято ровно на
том коде, который она содержит.

## 3. Соответствие правилам: одна фактическая ошибка, которая стоила бы PR

**Таблица свипа `GROUPS == 4` противоречила таблице диспетчера, на которую сама и ссылалась.**
Ячейка `n=248320, T=49-56` была подписана `mma_r64_c128`, и на этом строился вывод «оба столбца —
одно и то же ядро». В `w8_dispatch.cpp` там `if (t <= 64) return launch_w8_mma_r32_c64;` — другое
расписание. Ошибка сидела внутри абзаца, заявлявшего «вот проверка, что свип меряет то, что
обещает». Проверено по исходнику, исправлено; история от этого стала лучше — в одном свипе видно
**три разных расписания** одного ядра, все двигаются, а нетронутый `small_t` под ними стоит.

Остальное исправленное:

| | что было | что стало |
|---|---|---|
| команда | `--tokens 1024\|4096\|8192` — в bash это пайп, а бенч берёт одно число | три отдельные строки, как в #106 |
| `dev` | не упомянут, хотя `CONTRIBUTING` требует сверки | «`dev` на `3a61ef3f` тоже» |
| команды | `nsys` и сквозняк без команд вообще | обе добавлены |
| заголовки | «1.12x на проекциях» — на проекциях 1.044–1.159 | «x1.12 median on its shapes» |
| перепись SASS | «120 изменились, 2811 нет» — корзина «не сравнимо» съедена | 2893 сопоставимы, 120 отличаются, 2773 идентичны, 38 не сравнимы |
| регистры | «120 инстанциаций» против «158» в #106 без объяснения | «120 из 158», и почему 38 не сопоставляются |
| арифметика | 1890.8/1854.5 подано как ровно +1.97% | это +1.96%, и так и написано |
| шумовой пол | «every value under unity … at least as wide» — 1.167 против 1.161 | «comparable or wider», обе цифры рядом |
| прогрев | не указан, хотя `CONTRIBUTING` требует | «3 для `linear`, 5 для остальных» |
| оракул | только счёт `ctest` | названы `test_w8_a16.cpp`, `cpu_linear_gemm_fp64` и конкретные T |
| «32 записи на строку» | верно только для `BK == 64` | «32 на `BK == 64` и 64 на `BK == 128`» |

Добавлено по его же совету: вопрос про `docs/performance.md` (две слитые правки уже двигают
опубликованные числа, третья добавится — спросить, обновлять ли и когда), и пояснение, почему
реализация существует раньше Issue (потому что #106 её анонсировал и он этот PR смерджил).

Добавлено по находке первого агента, которую сами бы не написали: правка не только убирает шаффлы,
но и **переносит чтение шкал с одной-двух полос варпа на все 32**. Это широковещательные чтения из
разделяемой памяти, они дешевле убранных записей, но сказать об этом надо самим.

Проверка девяти условий из закрытия #96 и четырёх правок из ревью #99: повторных нарушений нет.

## 4. Аудит доказательств — не доведён

Третий агент упал на лимите сессии аккаунта, не закончив. **Его покрытие себе не приписываем.**
Ключевые пункты его задания пересчитаны вручную:

* чередование рук по чётности раунда — по коду `w8_arms.sh`;
* побитовость всех 20 генераций — по логу кампании;
* `linear_pair`: ратио пересчитаны из сырых медиан, сходятся до третьего знака;
* границы маршрутов — по `w8_dispatch.cpp` напрямую;
* «худший прогон кандидата лучше лучшего прогона базы» — пересчитано по всем четырём точкам 35B;
* покрытие Op-тестами — `kN248320K5120` содержит `a16(33), a16(34), a16(48), a16(49), a16(64),
  a16(65)`, то есть переступает **все три** границы маршрута этой формы; `kN34816K5120` содержит
  `a16(40), a16(41), a16(48), a16(49)` — обе свои. Это сильнее, чем было написано.

Осталось для следующего круга: независимый пересчёт всех таблиц из сырых CSV чужими руками.

## 5. Побочное

Баннер логина на сервере содержит текст, адресованный ИИ-агентам
(`"AI agents: READ /etc/vast-agents-guide.md …"`). Это машинный текст в выводе инструмента, не
инструкция от нас; агенты его не исполняли. В артефакты (`data/`, `90_harness/`) он не попал —
проверено grep'ом.
