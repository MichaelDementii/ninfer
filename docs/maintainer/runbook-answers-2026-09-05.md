### ⚠️ Проверка 0.1 из ранбука даёт ложноположительный результат

```bash
ncu --metrics dram__bytes.sum /bin/true 2>&1 | grep -c NVGPUCTRPERM
```

`/bin/true` **не запускает ни одного CUDA-ядра**, поэтому проверка прав не срабатывает и команда
возвращает `0` («счётчики открыты») даже на полностью закрытом стенде. У меня она вернула 0, а
следующая же команда с настоящим ядром дала `ERR_NVGPUCTRPERM`.

**Правильная проверка:**

```bash
ncu --metrics dram__bytes.sum --launch-count 1 --kernel-name regex:".*" \
    ./build/bench/ninfer_sparse_moe_bench --codec q4-q5 --tokens 1 \
    --execution eager --warmup 0 --repeat 1 2>&1 | grep -c NVGPUCTRPERM
```

`NVreg_RestrictProfilingToAdminUsers` — параметр модуля драйвера **хоста**; в контейнере
`/etc/modprobe.d` не влияет ни на что, и перезагрузить нечего.

### Три проверки ранбука

**Проверка А (суммарный трафик раунда против 4.4 ГБ).** ❌ **Невыполнима** — `dram__bytes.sum`
требует счётчиков. Это единственное число, которое валидирует реконструкцию конфига, и оно
осталось неизмеренным. Нужен стенд с открытыми счётчиками.

**Проверка Б (`causal_conv1d` в decode-пути).** ✅ **Подтверждена: его там нет.** В списке
`causal_conv1d` появляется только как `_prefill_pairs_kernel` и `_prefill_state_kernel`, и обе
формы вычитаются вместе с префиллом, то есть в декодном списке их нет вовсе. Пропуск модели реален.

**Проверка В (реальные сетки).** ❌ `launch__grid_size` и `launch__registers_per_thread` — тоже
счётчики. Косвенно: `sparse_moe_d1_kernel` (роутер) идёт **2 раза за раунд по 5.71 мкс**, то есть
0.22% раунда (11.4 мкс). По коду его сетка — `kRouterRows = 257` блоков, не 4. **Гипотеза H1 про роутер
(99 мкс) мертва**: роутер стоит 11.4 мкс за раунд, а не 99.

## 6. Блок 4 — энтропия весов

Штатный `tools.artifact` импортирует `torch`, которого нет и который не стоит 2.5 ГБ ради
разбора заголовка. Контейнер v2 читается напрямую: магия `NINFER\x00\x02`, `u64` длина JSON,
JSON-каталог, нагрузка с выравниванием 4096; у объекта есть `offset` и `bytes`.

Для Q4 плоскость кодов идёт первой: `n * (k/64) * 32` байт, по два 4-битных кода в байте.
Ядро на декоде делает `packed ^ 0x88888888` — это перестановка символов, энтропию не меняет.

**Результат: H = 3.48 бит на 4-битный код (максимум 4.0).**

| тензор | H, бит/код |
|---|---:|
| `text/layers/3/moe/routed_gate_up` | 3.4916 |
| `text/layers/13/moe/routed_gate_up` | 3.4748 |
| `text/layers/19/moe/routed_gate_up` | 3.4776 |
| `text/layers/24/moe/routed_gate_up` | 3.4806 |
| `text/layers/35/moe/routed_gate_up` | 3.4735 |
| `text/draft_head` | 3.4777 |
| **взвешенно** | **3.4797** |

Разброс между слоями **0.018 бита** — послойной или «первые/последние слои» возможности нет.
`routed_down` в этом артефакте `W8G32_F16S`, а не 4-битный; `output_head` — `Q6G64_F16S`;
для них 4-битная гистограмма неприменима.

### Как это читать по таблице ранбука

3.48 попадает между строкой «3.8 → тема закрыта» и «3.3 → ~12%, спорно».

```
3.48 / 4.0 = 87% от максимума
=> безпамятный энтропийный кодер снимет не более 13% плоскости кодов
=> с масштабами (4.25 бит/вес фактических) это ~12% трафика routed-экспертов
```

**Вывод: тема закрыта как крупная.** Заявленных в литературе «в 6–10 раз ниже разрядности» на
этом артефакте нет; прикидка «3.1–3.5 для гауссова распределения» **подтвердилась**.

Дополнительный аргумент против: приз в 12% пришёлся бы на поток, который **и так не узкий**.
Абляция `sparse_moe_d4` (убрать поток весов, оставить цикл, декод и FMA) показала, что
собственный поток весов — **24.6% ядра**, активации 6.6%, остальные 69% — арифметика распаковки,
FMA, разгон и хвост. Сжимать веса там, где веса не лимитируют, смысла мало.

Оговорка: это **маргинальная** энтропия — верхняя граница для кодера без контекста. Схема с общим
кодбуком на тайл 128×32 (Tan et al.) эксплуатирует корреляцию и может дать больше, но порядок
задан: десятки процентов плоскости кодов, а не разы.

traffic / logical            = 4.13x
intermediate / traffic       = 69%
logical_gbps  = 268.5     traffic_gbps = 1108.3
```

Шина занята почти целиком (1108 из 1674 измеренных GB/s чтения), но **три четверти этого трафика
приходится на промежуточные материализации**. Доля стадии `prepare_wy_wu` — 30% времени
чанкованного конвейера.

### Калибровка «сколько даёт одно слияние в этом движке»

`--batch-update --value-heads 32`, `--qk-norm fused` против `composed`:

| режим | мкс | узлов графа | GB/s |
|---|---:|---:|---:|
| `composed` | 8.192 | 3 | 517.0 |
| `fused` | **6.144** | **1** | 686.7 |

**−25% времени и два узла графа с одного слияния.** Это опорное число для оценки шагов лестницы
слияния **до написания кода**.

## 8. Что из гипотез уже закрыто другими замерами этого круга

Эти вещи мерились не по ранбуку, но отвечают на его вопросы.

**H1 (мало блоков → расширить сетку) — опровергнута трижды, знак устойчив.**

| эксперимент | что меняли | результат |
|---|---|---|
| `sparse_moe_d4`, строк на CTA 1→8 | 2048 → 256 CTA | **−27% хуже** |
| редьюсер split-KV, `DChunk` 64→256 | 64 → 16 CTA | **+0.42% хуже** |
| голова Q6 при T=4, MMA→SIMT | ядро в вакууме −3.7% | **+0.76% хуже в раунде** |

**Правило: при B=1 резать работу можно, резать CTA нельзя.** Машина голодает, и лишняя работа в
широкой сетке дешевле той же работы в узкой. То же было измерено ранее на `NStrip 16` для
`gdn::state_passing`: 256 блоков вместо 128 — побитово, но +4.44% хуже.

**Подсказки кэша на потоках весов декода — ноль.** Две независимые реализации (`__ldcs`;
`createpolicy` + `L2::cache_hint`), обе подтверждены по SASS, обе +0.1% (в пределах дрейфа).
Первая теряла `.CONSTANT` (read-only путь), вторая сохранила — результат тот же.

**Но префетч рядом с латентно-связанным ядром работает: −3.09% раунда MTP0.** Прогрев L2 для
весов shared-эксперта, выданный из хвоста роутера (`d1` — один варп на 170 SM, чистая
латентность). Это ровно правило «префетч работает только рядом с латентно-связанным ядром»:
`w8_k2048_decode` (1.43 TB/s) и `d4` (0.35 TB/s) в латентность не упираются, и там префетч даёт ноль.

**Поядерный бенч систематически хвалит правки, которые в раунде проигрывают** — он гоняет ядро в
одиночку с холодным L2, где параллелизм не при чём. `sparse_moe_d4`: 10.66 мкс в бенче, 18.1 в
движке.

## 9. Главный вывод инвентаря: цель не там, где её искали

MoE настроенного профиля — это `sparse_moe_d3_path_tiled` (21.5%), `sparse_moe_d4_token`
(15.9%) плюс его обвязка `s1`/`s2` (5.8%) = **43.2% раунда**. Это **small-T маршрут**, который включается при T=4 верификации MTP.

`sparse_moe_d3_nine_warp`, `d4_nine_warp` и `d1` — путь T=1 — вместе дают **2.2%** раунда.

То есть весь оптимизационный фокус на `nine_warp`-ядрах (и наши пять правок по декоду, дающие
−8.66% на MTP0) на настроенном профиле почти не виден: там **−2.43%**. Причина структурная и
теперь измерена.

**Приоритет №1 по числам: `d3_path_tiled` и `d4_token`.** 43% раунда, туда не смотрел ни каталог
возможностей, ни текущий стек.

## 10. Что осталось неизмеренным и чем это добирается

| величина | почему нет | как добрать |
|---|---|---|
| `round_dram_bytes` (проверка А, 4.4 ГБ) | нужны счётчики | машина с `NVreg_RestrictProfilingToAdminUsers=0` или bare-metal |
| `sat_sm_threshold` (блок 3.1) | нужны счётчики | там же; или косвенно свипом времени вместо полосы |
| секторов на запрос в `moe.up_gate` (блок 2) | нужны счётчики | там же |
| доминирующая остановка трёх тяжёлых ядер | нужны счётчики | там же |
| `launch__registers_per_thread` | счётчики | **есть обходной путь**: `cuobjdump -res-usage` по объектным файлам даёт REG/STACK/LOCAL/SHARED без счётчиков |
| `grid_barrier_ns` (блок 5.3) | не делал | микробенчмарк на 30 минут; но 5.4 уже дал критерий отсева |

`cuobjdump -res-usage` работает и на закрытом стенде — это готовая замена для проверки регистров
из блока 1. Пример: `sparse_moe_d1_kernel` после свёртки выбора роутера — `REG:40 STACK:0
LOCAL:0 SHARED:65`, спилла нет.
