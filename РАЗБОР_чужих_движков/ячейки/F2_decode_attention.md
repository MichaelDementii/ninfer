# F2 — декодное внимание и страничный KV: FlashInfer и XQA против нашего

## Что это за механизм

В корпусе четыре независимых декодных ядра, и это разные точки проектирования.
(1) **TensorRT-LLM XQA `mha.cu`** — production-ядро NVIDIA для генерации; именно оно выбирается
FlashInfer'ом по умолчанию на sm_120/sm_121 (`flashinfer/flashinfer/decode.py:3321`), и в нём есть
тюнинговые константы конкретно под `__CUDA_ARCH__ == 1200/1210`. Тензорноядерное, сетка
(запрос × KV-голова × кусок KV), **свёртка split-KV встроена в тот же запуск** через глобальный
семафор «последний пришедший CTA сливает», куски KV раздаются CTA **чересполосно**, а масштаб
кванта — один скаляр на весь тензор, вложенный в два fp32-множителя.
(2) **Форк XQA внутри FlashInfer (`flashinfer/csrc/xqa/`)** — то же ядро плюс **KV-кеш в NVFP4**
(`__nv_fp4_e2m1` + масштаб `__nv_fp8_e4m3` на каждые 16 элементов) и head_dim до 512.
(3) **FlashInfer `decode.cuh`** — скалярное ядро без тензорных ядер; интересно только двумя
вещами: измеряемой рантаймом занятостью в политике сплитов и однопроходным векторным редуктором.
(4) **FlashMLA-порт под sm_120** (`sparse_mla_sm120/decode_*`) — масштабы кванта лежат в одной
записи с кодами, один bulk-копир забирает и то и другое.

Все три «взрослых» реализации сходятся в том, что число сплитов выбирается **монотонной**
формулой «заполнить одну волну SM», а не таблицей тиров по длине контекста.

## Доказательства из кода

Сокращения путей: **T/** = `trtllm/cpp/kernels/xqa/`, **F/** = `flashinfer/csrc/xqa/`,

### 2. Разбор ядра XQA `mha.cu`

**Сетка.** `T/mha.cu:1544-1545` — «gridDim: x — K/V sequence-dim split; y — number of K or V heads;
z — number of requests». Запуск `T/mha.cu:2894-2900`. 8 варпов, 256 нитей,
`ctaShapeInWarps = {4,1,2}` (`T/mha.cu:63`), `ctaTile = {256, 16}` (`T/mha.cu:83-84`) — CTA
съедает **256 токенов KV** за итерацию. `warpIdx.z` = роль: z=0 считает QK^T (по 64 колонки KV
на варп), z=1 считает PV (`T/mha.cu:79-81`: `gemm1WarpsPerGrp = headElems/warpTile.x`; при
head_dim 256 это 4 варпа на всю ширину головы, без деления по KV). Дробления по Q-головам нет:
`T/mha.cu:74-77` — `nbValidRows = headGrpSize * beamWidth`, `warpTile = {64, roundUp(nbValidRows,16)}`.

**Число сплитов.** `T/mha.cu:2808-2825`:
```cpp
return std::min<uint32_t>(
    std::max<uint32_t>(1U, prop.multiProcessorCount / (batchSize * nbKHeads)),
    divUp(maxSeqLen, ctaTile.x));
```
Никаких тиров: «столько CTA на голову, сколько влезает в волну», сверху ограничено числом
KV-тайлов. Монотонно по `maxSeqLen` по построению. Идентичная формула в форке FlashInfer
(`F/mha.cu:3026-3029`). Есть env-override `XQA_NB_SUB_SEQ` (`T/mha.cu:2814-2822`, `T/README.md:26`).

**Раздача кусков — чересполосная, не сплошная.** `T/mha.cu:1740-1742` и `:1917`:
```cpp
uint32_t const seqStrideIters = nbSubSeqPerSeq;
uint32_t const seqIterInit = nbSkipLeadingTiles + idxSubSeqInSeq;
...
for (uint32_t seqIter = seqIterInit; seqIter < nbSeqIters; seqIter += seqStrideIters)
```
CTA i берёт тайлы i, i+N, i+2N… Следствие в адресации страниц: курсор двигается на
`nbPagesPerCtaTile * nbSubSeqPerSeq` (`T/mha.cu:1874`). Все CTA идут по кешу **одним фронтом**.

**Свёртка split-KV внутри того же запуска.** `T/mha.cu:2616-2630`:
```cpp
uint32_t const lastOld = nbSubSeqPerSeq - 1;
asm volatile("atom.acq_rel.gpu.global.inc.u32 %0, [%1], %2;\n"
             : "=r"(old) : "l"(&semaphores[idxSeq]), "r"(lastOld));
mbsmem.isLastCta = (old == lastOld);
```
`atom.inc` с wrap-значением сам обнуляет семафор к следующему запуску. Второго ядра нет.
Сама редукция — `T/mha.cu:2631-2718`: `mergeRowMax<8>` (8-глубокий программный конвейер по
максимумам, `T/mha.cu:2638`), затем двубуферный `cp.async` частичных тайлов
(`T/mha.cu:2647-2674`) и слияние (`T/mha.cu:2676-2684`).

**Частичный выход хранится уже нормированным.** `T/mha.cu:2509-2524` — перед записью в scratch
аккумулятор делится на **свой** `globalRowSum` и умножается на `voScale`, и только потом
`toFp16(acc)`; при слиянии умножение возвращается обратно (`rescaleAcc(warp, tile, ...,
scaledTileRowSum)`, `T/mha.cu:2682`). Это держит fp16-частичное значение в узком диапазоне при
тех же байтах. `m` и `d` — fp32 (`SMemWarpRowMax`, `T/mha.cu:324`).

### 3. Разбор ядра FlashInfer `decode.cuh`

- `FI/decode.cuh:64-115` и `:130-145` — QK и PV на FFMA, редукция по head_dim через `shfl_xor`.
  Тензорных ядер нет вовсе.
- `FI/decode.cuh:670-671` — `vec_size = max(16/sizeof(DTypeKV), HEAD_DIM/32)`: каждая нить всегда
  читает ровно 16 байт.
- **Кеш адресов страниц.** `FI/decode.cuh:483-490` — до цикла CTA кооперативно считает `bdx`
  будущих смещений в `kv_offset_smem`; в цикле пересчёт только `if ((iter + num_stages_smem)
  % bdx == 0)` (`:525-534`), а сам цикл читает готовые `size_t` (`:549-554`).
  `page_size` — `uint_fastdiv`.
- **Политика сплитов.** `FI/decode.cuh:703-714`:
  ```cpp
  cudaOccupancyMaxActiveBlocksPerMultiprocessor(&num_blocks_per_sm, kernel, num_threads, smem_size);
  max_grid_size = num_blocks_per_sm * num_sm;
  kv_chunk_size = max(ceil_div(seq_len, max_grid_size / num_kv_heads), 256);
  ```
  Занятость **измеряется рантаймом**; пол — 256 ключей на кусок. Batch-вариант —
  `FI/scheduler.cuh:74-98` (бинарный поиск минимального числа страниц на кусок при
  `new_batch_size * gdy <= max_grid_size`) с полом `max(128/page_size, 1)` (`:198`).
- **Редуктор.** `FI/persistent.cuh:596-640` и `FI/cascade.cuh:281-340`:
  `vec_size = max(16/sizeof, HEAD_DIM/32)` (`persistent.cuh:524-525`) — **16 байт на нить**;
  LSE грузится пачкой в `s_smem` раз в `bdx` итераций (`persistent.cuh:613-617`,
  `cascade.cuh:309-313`); конвейер `cp.async` глубины 4 (`persistent.cuh:685`);
  **один проход** онлайн-слияния `st.merge(v, s, 1)` (`persistent.cuh:624`);
  единица работы — **варп** на (строка, KV-голова) (`persistent.cuh:566-568`).

### 4. Кванты KV

**XQA: масштаб один на весь тензор и не применяется к элементам вообще.**
`T/mha.h:135-136` — `float const* kvCacheScale; // Device memory scalar. Same scale for K and V`.
Он вкладывается в два fp32-скаляра вокруг softmax: `T/mha.cu:1756-1757`
`qkScale = qScale * kvCacheScale[0] * rsqrtf(validElemsPerHead)` (применяется к аккумулятору
после MMA, `T/mha.cu:1999`) и `T/mha.cu:2509, 2520-2522` `voScale = kvCacheScale[0]`.
Сама конверсия fp8/int8 → f16 идёт **в регистрах между `ldmatrix` и `mma`**, по 32-битному слову
(`T/mha.cu:1106-1129` для K, `:1248-1275` для V), аппаратной инструкцией
`cvt.rn.f16x2.e4m3x2` (`T/utils.cuh:809-837`); для V порядок элементов чинится бесплатным
`prmt.b32 ..., 0x3120` (`T/utils.cuh:855`).

**XQA не квантует Q в основном ядре.** Вместо этого он **один раз переставляет строки Q**, чтобы
дешёвый порядок распаковки K совпал: `T/mha.cu:1904-1912`
`reorder16bQHeadsToMatch8bKCache<...>` (`T/mhaUtils.cuh:209-246`), обратная перестановка
применяется к выходному тайлу (`T/mha.cu:2554`). На sm_90 и в MLA Q, наоборот, реально в fp8
(`T/mha_sm90.cu:117`, `T/defines.h:38-41`).

**MMA.** `T/mma.cuh:29-70` — `m16n8k16.f32.f16.f16.f32`, `.bf16.bf16.`, и
`m16n8k32.f32.e4m3.e4m3.f32`. Но поскольку `mha.cu` поднимает кеш до `InputElem`, **в `mha.cu`
всегда исполняется fp16/bf16 HMMA, а fp8-QMMA — никогда**; QMMA появляется только в
`mha_sm90.cu` (wgmma) и `mla_sm120.cu` (`T/mla_sm120.cu:840, 903, 1425`). Аккумулятор всюду fp32
(`T/mha_components.cuh:5-8`).

**NVFP4-путь форка FlashInfer.** Коды `__nv_fp4_e2m1` по 2 в байте, масштаб `__nv_fp8_e4m3`
на каждые 16 элементов (`F/defines.h:238-243`). Масштабы живут в **отдельном страничном пуле**
(`F/mha.cu:2978` `GMemCacheHeadSf* kSfCacheVLLM, vSfCacheVLLM`), стейджатся в свои smem-буферы
`kSf`/`vSf` (`F/mha.cu:359-360`, размеры `:340-349`), грузятся зёрнами по 4 байта
(`F/mha.cu:68` `grainBytesSf = 4`) теми же `copyPartialHeadsAsync`/`copyHeadsAsync`
(`F/mha.cu:1915-1916`, `:2272-2273`, `:2296-2297`), префетчатся в регистры 32-битными LDS
(`F/mha.cu:1049-1050`, `:1209`). Распаковка — `cvt.rn.f16x2.e2m1x2` (`F/utils.cuh:757-770`).
Прямая распаковка в bf16 (`cvt.rn.bf16x2.e2m1x2`) закрыта гейтом
`__CUDA_ARCH__ >= 1000 && CTK >= 13.2` (`F/utils.cuh:778-795`) с явным запасным путём
«convert e2m1 -> fp16 -> bf16» (`F/utils.cuh:796-806`) — это ровно то, что бриф фиксирует про
sm_120a («fp4 распаковывается только в f16»).

**FlashMLA sm_120: масштабы в одной записи с кодами.**
`FI/sparse_mla_sm120/decode_dsv3_2_kernel.cuh:29-35`, дословно:
```
KV gmem layout per token (KV_GMEM_STRIDE=656):
  [0     : 512)  FP8 e4m3 nope, 4 tiles × 128 elements
  [512   : 528)  4 × FP32 scale (one per 128-elem tile)
  [528   : 656)  BF16 rope
... The IO warp does a single bulk per token that covers both nope and inline
scales in one go (528 B) ... No scalar scale gather phase.
```
Второй вариант — **хвост страницы**: `FI/sparse_mla_sm120/model/kv_cache_traits.cuh:108-119`
(данные 576 Б на токен, 16-байтно выровнены; масштабы `[block_size*576 : block_size*584)`,
8 Б на токен, формат `ScaleFormat::UE8M0_BYTE` — **масштаб = один байт экспоненты**);
адресация `FI/sparse_mla_sm120/common/kv_cache_io.cuh:104-109`.
`kv_cache_traits.cuh:83-87` — `scale_to_ue8m0(float) = (bits >> 23) & 0xFF`.
`FI/sparse_mla_sm120/common/scale_mma.cuh:67-99` — при степенно-двоичном масштабе он подаётся
операндом блочно-масштабированного MMA и аккумулятор не сбрасывается между блоками
(`init_qk_acc` копит дальше, `commit_qk_acc` просто пишет `qk[i] = acc_i`); произвольный
fp32-масштаб стоит **двух проходов MMA** (`scale_mma.cuh:42-45`).

### 5. Пачка строк (спекуляция)

- `T/defines.h:63-73` — `SPEC_DEC`, `M_TILESIZE` (умолчание 32; инстанцируется 16 и 32,
  `T/gen_cubins.py:453`).
- `T/mha.cu:69-77` — при `SPEC_DEC` `nbValidRows = rowsPerBlock` вместо `headGrpSize*beamWidth`,
  то есть `warpTile.y` растёт с 16 до 32. **Тензорные ядра используются и при T=1, и при T>1** —
  многострочный путь просто перестаёт тратить половину строк MMA впустую. Строка = плоская пара
  (токен, Q-голова): `T/mha.cu:1650-1652`.
- **Порога по T нет**: переключение чисто compile-time. Хост режет `qSeqLen * headGrpSize` строк
  на блоки по `rowsPerBlock` и **каждый блок строк — отдельный CTA**, `T/mha.cu:2896-2897`:
  ```cpp
  const uint32_t nbTokenBlocksPerGrp = divUp(qSeqLen * headGrpSize, rowsPerBlock);
  dim3 const dimGrid{nbSubSeqPerSeq, nbKHeads * nbTokenBlocksPerGrp, batchSize};
  ```
  То есть при grp=8 и `M_TILESIZE=32`: T∈[1,4] — один блок, T∈[5,8] — два, и **KV читается
  заново на каждый блок строк**.
- **Эвристика сплитов при этом не меняется**: `computeNbSubSeqPerSeqMHA` не видит `qSeqLen`
  (`T/mha.cu:2808`), так что при спекуляции суммарная сетка = `nbSubSeqPerSeq × nbKHeads ×
  nbTokenBlocksPerGrp × batchSize` и **выходит за одну волну**. Scratch и семафоры тоже растут
  в `nbTokenBlocksPerGrp` раз (`T/mha.cu:2561-2577`).
- Маска — битовая матрица `[nbReq][qSeqLen][divUp(qSeqLen,32)]` (`T/specDec.h:23-28`),
  применяется только к тайлам, которые могут пересечься с окном черновика
  (`T/mha.cu:2019-2035`, порог `nbSeqItersWithoutMask`, `T/mha.cu:1737`). **Маскируется не в
  `-inf`, а в конечное `safeInitRowMax = -1e5`** (`T/utils.cuh:44`, `T/mha.cu:604`).
- SWAP_AB (M на оси токенов вместо оси Q-голов) есть **только у sm_90**
  (`T/mha_sm90.cu:43-58`, `flashinfer/flashinfer/jit/xqa.py:36-39, 48-50`), в `mha.cu` его нет.
  Условие применимости — `q_seq_len * head_group_ratio <= 32`.
- Древовидный режим существует (`IS_SPEC_DEC_TREE`, `T/defines.h:199-201`), но FlashInfer его
  выключает (`flashinfer/flashinfer/jit/xqa.py:131`).

### 6. Длинный контекст

- В `T/*` **ноль** упоминаний `attentionChunkSize`, `kvIndices`, разреженного KV, иерархии страниц.
  Единственный механизм — sliding window (`T/defines.h:128-130`): он пропускает целые ведущие
  тайлы и целые ведущие страницы, не трогая их память (`T/mha.cu:1714-1730`,
  `nbSkipLeadingPages`/`nbSkipLeadingTiles`, ragged-первый тайл маскируется на
  `T/mha.cu:2037-2051`). Плюс attention sinks (`T/mha.h:118`, `T/mha.cu:1473-1493`).
  Совмещение sliding window с древовидной спекуляцией запрещено (`T/mha.cu:1716`).
- Разреженность есть только в MLA-ветке: `FI/sparse_mla_sm120/common/kv_cache_io.cuh:74-79` —
  gather 64 произвольных токенов по top-k индексам.
- `flashinfer/flashinfer/decode.py:3348-3352` — `skip_softmax_threshold_scale_factor`
  («skip-softmax sparsity», arXiv 2512.12087) — только в backend `trtllm-gen`, то есть sm_100.

### 7. Ширина доступа и подсказки кешу

- **Самая широкая загрузка KV — 128 бит, `cp.async.cg`.** `T/utils.cuh:550-551`
  (`LdGrain = Vec<uint32_t,4>`), `T/ldgsts.cuh:40-52`:
  ```cpp
  asm volatile("cp.async.cg.shared.global [%0], [%1], 16, %2;\n" ...);
  ```
  Подсказка `L2::128B` **закомментирована**, с объяснением `T/ldgsts.cuh:28`:
  `// @fixme: prefetch makes it slower on sm_86. Try on other platforms.`
- Единственное место с политикой кеша — чтение длины последовательности, которое перечитывают
  все CTA всех сплитов (`T/mhaUtils.cuh:273-286`):
  ```cpp
  asm("createpolicy.fractional.L2::evict_last.b64 %0;\n" : "=l"(cachePolicy));
  asm("ld.global.nc.L1::evict_last.L2::cache_hint.L2::256B.b32 %0, [%1], %2;\n" ...);
  ```
  На **сам поток K/V никаких подсказок нет**, и это открытые TODO авторов:
  `T/mha.cu:1954` `// @fixme: do L2 cache prefetch for next iter tile if last part`,
  `T/mhaUtils.cuh:113` `// @fixme: give evict first hint for last part.`
- Латентность прячется мультибуферизацией: `nbKBuffers = nbVBuffers = 2`, `nbXBuffers = 1`
  (`T/mha.cu:120-123`) с честным комментарием `// @fixme: H100 SXM need more in-flight requests`;
  следующая часть K грузится до потребления текущей (`T/mha.cu:1946-1961`, `waitGroup<1>`).
  В sm_120-родном MLA-ядре глубина уже 12 (`T/mla_sm120.cu:336`).
- PDL включён по умолчанию (`T/defines.h:147-149`, `T/mha.cu:1632-1635` `preExit(); acqBulk();`),
  но форк FlashInfer снижает его до наивного на sm_120 (`F/defines.h:132-143`).

## Кандидаты для NInfer

### 1. NVFP4 KV-кеш (сначала только V, потом K)

**Механизм.** Форк XQA внутри FlashInfer держит KV-кеш в `__nv_fp4_e2m1` с масштабом
`__nv_fp8_e4m3` **на каждые 16 элементов** (`F/defines.h:235-244`), масштабы — в отдельном
страничном пуле (`F/mha.cu:2978`), стейджатся теми же `copyHeadsAsync` зёрнами по 4 байта
(`F/mha.cu:68`, `:2272-2273`) в отдельные smem-буферы (`F/mha.cu:340-360`), распаковываются
`cvt.rn.f16x2.e2m1x2` (`F/utils.cuh:757-770`) и умножаются на масштаб уже в регистрах
(`F/mha.cu:1026-1050` для K, `:1195-1272` для V). MMA после этого — обычный f16.
На d=256: **128 Б кодов + 16 Б масштабов = 144 Б** на тензор на голову на токен против наших
264 Б (int8 g64) и 258 Б (fp8 g256).

Два шага, разной цены и риска:
- **1a — только V.** V у нас и так проходит через явный деквант в bf16
  (`small_t_i8.cuh:539-557`); заменить источник на fp4 + fp8-масштаб на 16 элементов и
  распаковывать `cvt.rn.f16x2.e2m1x2` в f16, после чего PV идёт через уже существующий
  `mma_f16` (`mma.cuh:42-49`, тот же f32-аккумулятор). K не трогаем — путь «int8 прямо в
  `mma_s8` без декванта» сохраняется целиком. Байты: 264 + 144 = 408 против 528, **−22.7 %**.
- **1b — и K.** K распаковывается в f16 и QK уходит с `mma_s8` на `mma_f16`. Байты 288 против
  528, **−45.5 %**.

**Ожидаемый эффект.** Прямо по roofline (таблица выше): 1b даёт на 35B при 200k
1178 → 643 мкс нижней границы чтения KV, на 27B 3.69 → 2.06 мс; 1a — примерно половину этого.
При доле внимания ~45 % шага на 200k это **−20 % (1a) / −40 % (1b) времени декодного шага
на длинном контексте**; на 32k доля внимания ~11 %, эффект 2.5 % / 5 %.
Плата по ALU: QK-MMA при 1b удваивается (m16n8k16 f16 вместо m16n8k32 s8) плюс распаковка
128 Б кодов на ключ. Запас ×9 по ALU превращается примерно в ×4 — всё ещё memory-bound,
но это надо подтвердить профилем, а не считать.

**Чем меряем.** Сначала **точность**, потому что весь кандидат об неё и разбивается: прогон
точностной батареи (стенд A) на 35B и 27B с V-в-fp4 (1a) и с K+V-в-fp4 (1b) против текущего
int8 g64 / fp8 g256. Важный аргумент в пользу того, что это не «int4»: эффективная гранулярность
кванта **улучшается** с 64 (наш int8) до 16 (NVFP4), и формат e2m1 с блочным масштабом — тот же,
что уже несут веса MLP 27B. Затем скорость: свип по S ∈ {8k, 32k, 128k, 200k}, T ∈ {1,4},
метрика — мкс на слой и доля от `S × KVHeads × байт_на_токен / 1792 ГБ/с`.

**Риски и что ломается.** Точность — главный. Вывод не побитов ни в каком варианте. Формат
кеша меняется: `d256_profile.h`, новый кодек рядом с `int8_g64_codec.cuh`, `kv_cache/append`,
оба small_t-ядра, оба prompt-ядра, аллокатор страниц, сериализация кеша. Регистровое давление
в продюсер-варпе растёт (распаковка + масштабы K в регистрах). Прямой распаковки fp4→bf16 на
sm_120a нет (бриф; подтверждено гейтом `F/utils.cuh:782-784`), значит PV придётся вести через
f16-операнды — что уже и так делают оба prompt-ядра (`prompt_i8.cuh:440`, `prompt_fp8.cuh:422`).

**Оценка объёма.** 1a: ~5-6 файлов (новый кодек, append, `small_t_i8.cuh`, `small_t_fp8.cuh`,
профиль, аллокатор). 1b: плюс переписанный QK в обоих small_t и в обоих prompt — ~10-12 файлов.
Это самый большой кандидат ячейки и по эффекту, и по объёму.

### 2. Сделать device-side политику сплитов монотонной (она уже оплачена хостом)

**Механизм.** `causal_small_t_split_upper_bound` (`small_t.cu:28-41`) — монотонная огибающая по
тирам; именно она задаёт `gridDim.y`. `causal_small_t_default_splits` (`small_t.cuh:81-94`) —
однотировая, немонотонная; именно она задаёт `active_split_count`, а CTA с
`split >= active_split_count` выходит на `small_t_i8.cuh:188`. На границах тиров (4096, 8198,
16390) активное число CTA падает вдвое **при уже запущенной сетке**:

| окно S (35B) | активных CTA | запущено CTA | доля волны сейчас | стало бы |
|---:|---:|---:|---:|---:|
| 4096 | 256 | 256 | 75.3 % | 75.3 % |
| **4097** | 130 | 256 | **38.2 %** | 75.3 % |
| 8198 | 258 | 258 | 75.9 % | 75.9 % |
| **8199** | 130 | 258 | **38.2 %** | 75.9 % |
| 12000 | 188 | 258 | 55.3 % | 75.9 % |
| 16390 | 258 | 258 | 75.9 % | 75.9 % |
| **16391** | 138 | 258 | **40.6 %** | 75.9 % |
| 20000 | 168 | 258 | 49.4 % | 75.9 % |
| 24000 | 200 | 258 | 58.8 % | 75.9 % |
| 32768 | 274 | 274 | 80.6 % | 80.6 % |
| ≥40800 | 340 | 340 | 100 % | 100 % |

(27B тот же профиль: 38.8 % при 4097 и 8199, 41.2 % при 16391.)
Правка: `causal_small_t_default_splits` заменить на device-твин
`causal_small_t_split_upper_bound`. Эталоны монотонности: `T/mha.cu:2823-2824` и
`FI/decode.cuh:713` — обе формулы монотонны по seq_len по построению.

**Ожидаемый эффект.** Декод, окна 4k..40k. Байты KV не меняются; растёт число CTA, которые их
тянут. При 138 CTA в полёте 2.3 МБ < 2.7 МБ, нужных для насыщения 1792 ГБ/с, при 258 — 4.4 МБ.
Ожидаемая доля пика HBM растёт с ~50-60 % до ~85-95 %; на слое 35B при 20k это 17.3 МБ /
1792 ГБ/с = 9.7 мкс на пике против сегодняшних ~16-19 мкс. Плата: частичные суммы при 129
сплитах вместо 69 — +6 % трафика (2.1 МБ вместо 1.1 МБ на 17.3 МБ полезных). Чистый выигрыш
ожидается **+15..35 % на декодном внимании в этом окне**.

**Чем меряем.** Свип по S ∈ {4096, 4097, 6000, 8198, 8199, 12000, 16390, 16391, 20000, 24000,
32768} при T=1 и T=4, A/B `default_splits` vs `split_upper_bound`; метрика — мкс на слой и доля
от 1792 ГБ/с. Снять и на I8, и на FP8 (у fp8 свой особый случай для T=1,
`small_t.cuh:122-130`).

**Риски.** Вывод **не побитов**: меняется число слагаемых в свёртке онлайн-softmax. Нужна
точностная батарея. Спецслучаи T=5/6 (`small_t.cuh:101-115`) трогать нельзя — менять только
default-ветку. Занятость и регистры не меняются, сетка не меняется (она уже такая).

**Объём.** 1-2 файла, ~30 строк. Лучшее отношение эффекта к диффу в ячейке.

### 3. Переписать редуктор split-K: 16-байтные чтения, статистика в smem, один проход

**Механизм.** Третий проход (`small_t.cuh:250-260`) на каждый сплит делает три глобальных чтения
на нить: `partial_l`, `partial_m` и один `bf16` из `partial_acc`. При 170 сплитах и 64 активных
нитях это 170×3×64 = 32 640 инструкций загрузки на CTA ради 21.8 КБ полезных байт —
**2 байта на инструкцию вместо 16**. Эталоны: `FI/persistent.cuh:524-525` (16 Б на нить),
`FI/persistent.cuh:613-617` и `FI/cascade.cuh:309-313` (LSE пачкой в `s_smem` раз в `bdx`
итераций), `FI/sparse_mla_sm120/decode_dsv4_kernel.cuh:813-824` (все LSE сплитов в динамический
smem до цикла), `FI/persistent.cuh:624` (`st.merge` — один проход вместо трёх),
`FI/persistent.cuh:566-568` (единица работы — варп, не блок из 256 нитей).

- **3a (побитово нейтральная).** Оставить три прохода и порядок суммирования, но: (i) сохранить
  прочитанные `partial_m`/`partial_l` в smem во время первых двух проходов; (ii) дать каждой
  нити 8 подряд идущих `d` и читать `partial_acc` одним `int4`.
- **3b.** Однопроходное онлайн-слияние с `cp.async` глубины 4, варп на (голова, токен).
  Выход не побитов.

**Ожидаемый эффект.** Редуктор на 35B при T=1 читает 1.39 МБ и запущен на 64 CTA из 170 SM.
Полезные байты — 0.78 мкс на пике; текущая инструкционная стоимость при 64 занятых SM ≈
32 640×64 / (64×4) / 2.4 ГГц ≈ **3.4 мкс**, то есть ~18 % времени декодного внимания на слой
при 32k (19.3 мкс). После 3a остаётся ≈0.28 мкс инструкций + латентность → ожидаемо 1.0-1.5 мкс,
то есть **−10 % на декодном внимании**. Дополнительно: `DChunk = 64` при блоке 256 нитей
означает, что 192 нити из 256 в третьем проходе простаивают (`small_t.cuh:246`).

**Чем меряем.** Изолированный запуск редуктора при splits ∈ {32, 69, 137, 170}, T ∈ {1,4};
метрика — мкс и доля от 1792 ГБ/с на `splits × QHeads × 256 × 2` байт. Для 3a — проверка
побитового равенства на фиксированном входе.

**Риски.** 3a — регистровое давление (8 значений `d` на нить) и +`splits × 8 Б` shared memory
(170 сплитов → 1.4 КБ). 3b ломает побитовость. Partial-ядро не трогается.

**Объём.** 1 файл (`small_t.cuh`), для 3b ещё сетка в `small_t.cu`. ~80-150 строк.

### 4. Чересполосная раздача кусков KV вместо сплошных отрезков

**Механизм.** XQA раздаёт CTA не сплошные диапазоны, а тайлы через шаг `nbSubSeqPerSeq`
(`T/mha.cu:1740-1742`, `:1917`, курсор страниц `:1874`). У нас — сплошные отрезки
(`small_t_i8.cuh:190-196`). Разница в том, **где в DRAM находятся 340 CTA одновременно**: при
сплошной раздаче на 200k они читают 340 областей, разнесённых на ~600 токенов; при чересполосной
все 340 идут одним фронтом по ~10 880 подряд идущим токенам (340 × Bc=32), то есть по одной
непрерывной области ~5.7 МБ. Это меняет попадания в открытую строку DRAM и в TLB, и делает
чтение таблицы страниц общим для всех CTA (одни и те же элементы → L2).
Реализуемо у нас: smem-кеш страниц (`physical_pages_s[64]`) вместо сплошного диапазона
собирается с шагом — при 200k, 170 сплитах и Bc=32 у CTA 37 тайлов, то есть 37 индексов, что
влезает в существующие 64 слота.

**Ожидаемый эффект.** Байты не меняются. Меняется достигаемая доля пика HBM — величина, которую
эта ячейка как раз и не может посчитать заранее. Ставлю кандидатом, а не «сделать»: цена
эксперимента низкая, но арифметики под него нет.

**Чем меряем.** A/B на S ∈ {32k, 128k, 200k}, T=1, метрика — доля от
`S × KVHeads × 528 / 1792 ГБ/с`. Показатель успеха — рост доли пика; если он не растёт,
механизм закрыт одним замером.

**Риски.** Разбиение softmax по сплитам меняется → **вывод не побитов**. Ломается предположение
о сплошном диапазоне сразу в трёх местах: сборка `physical_pages_s` (`small_t_i8.cuh:203-207`),
условие вплавленного append `position >= split_start && position < split_end`
(`:220`, `:236`) и маска `key >= split_start && key < split_end` (`:476-489`). Все три
переписываются на «принадлежит ли ключ множеству тайлов этого CTA», это дешёвая арифметика,
но её надо не сломать.

**Объём.** 2-3 файла (`small_t_i8.cuh`, `small_t_fp8.cuh`, `small_t_bf16.cuh`), ~60 строк.

### 5. Конечный часовой вместо `-inf` в маске

**Механизм.** XQA маскирует не в `-inf`, а в конечное `safeInitRowMax = -1e5`
(`T/utils.cuh:44`, применение `T/mha.cu:604`), и поэтому в его онлайн-softmax **нет ни одного
предиката против NaN**. FlashInfer делает то же иначе — зажимает максимум
(`FI/decode.cuh:104-106`, «Per-row clamp: fully masked tiles yield exp2(-inf) = 0, not NaN»).
У нас продюсер-варп несёт всю цепочку предикатов: четыре тернарника на `nt` при маскировании
(`small_t_i8.cuh:475-490`), два на `alpha` (`:499-500`) и ещё четыре на `nt` при `exp2`
(`:507-518`). При QKNt=4 это ~18 сравнений и селектов на тайл на нить продюсера — а при **T=1
продюсер это 1 варп из 8**, и он стоит на критическом пути перед `__syncthreads`
(`small_t_i8.cuh:559`).

**Ожидаемый эффект.** Не по байтам, а по критическому пути продюсера. Оценить в микросекундах
заранее нельзя — надо смотреть, упирается ли тайловая итерация в продюсера или в память;
при глубине конвейера 1 и полном барьере на тайл (`:604-605`) продюсер вполне может быть
на пути. Дешёвый эксперимент.

**Чем меряем.** A/B на S ∈ {8k, 32k}, T ∈ {1, 4}: мкс на слой. Плюс проверка, что при полностью
замаскированном сплите `l == 0` и редуктор его отбрасывает.

**Риски.** Редуктор различает «пустой сплит» по `head_m == -CUDART_INF_F`
(`small_t.cuh:217`) — с конечным часовым это условие перестаёт срабатывать и надо переключиться
на `head_l > 0`, которое уже проверяется (`:229`, `:249`). `exp2` от -1e5·log2e даёт ровно 0.0,
как и текущий явный `0.0f`, так что в непустых сплитах результат **побитово тот же**;
меняется только вырожденный случай. Часовой применяется после умножения на `scale`
(`small_t_i8.cuh:477`), иначе он масштабируется.

**Объём.** 2-3 файла, ~40 строк.

### 6. Одна запись на страницу для кодов и масштабов + 16-байтная загрузка масштабов

**Механизм.** FlashMLA держит масштабы либо встык с кодами внутри токена (INLINE, 656 Б, один
bulk — «no scalar scale gather phase», `FI/sparse_mla_sm120/decode_dsv3_2_kernel.cuh:29-35`,
`model/kv_cache_traits.cuh:57-73`), либо **хвостом страницы** (FOOTER,
`kv_cache_traits.cuh:108-119`, адресация `common/kv_cache_io.cuh:104-109`). У нас четыре
независимых тензора → четыре потока запросов на CTA, то есть 1360 одновременных потоков к DRAM
при 340 CTA. FOOTER для нашей страницы 64 токена:
`[64×256 K][64×256 V][64×4 K-scale][64×4 V-scale]` = 33 280 Б на (страницу, голову), одна база,
**байты не меняются**, 16-байтное выравнивание сохраняется (16384 и 512 кратны 16).

Отдельный бесплатный мини-шаг: масштабы грузятся `cp_async<8>` и только нитями `tid < Bc`
(`small_t_i8.cuh:360-366`). Смещение `kv_cache_int8_quant_scale_index` кратно 4 половинкам,
тайл всегда начинается с кратного 32 — значит для чётного `page_offset` адрес 16-байтно
выровнен и можно грузить **по два ключа одним `cp_async<16>`**, вдвое сократив число запросов.
Ровно так уже сделано в fp8-ядре (`small_t_fp8.cuh:314-323`: `for chunk < Bc/8` с
`cp_async_zfill<16>`).

**Ожидаемый эффект.** Байты HBM не меняются. Эффект — в эффективности DRAM и в числе запросов;
считать заранее нечем, мерить той же метрикой «доля пика». Мини-шаг с `cp_async<16>` снимает
32 запроса на тайл на CTA из ~1088 — около 3 %.

**Чем меряем.** Свип по S ∈ {32k, 128k, 200k}, T=1. Начинать с мини-шага, он не трогает
раскладку памяти вовсе.

**Риски.** Полная FOOTER-раскладка — это `kv_cache/append`, оба кодека, оба prompt-ядра, оба
small_t-ядра и аллокатор страниц; ломается любой сохранённый кеш. Численность и побитовость
**не меняются вообще** — переставляются только адреса. Мини-шаг — 5 строк, тоже побитово нейтрален.
Замечу, что кандидат 1 всё равно потребует новой раскладки — эти два стоит делать одним заходом.

**Объём.** Мини-шаг: 1 файл, ~10 строк. FOOTER: ~8-10 файлов.

### 7. Поднять `TokenTile` выше 6

**Механизм.** `causal_attention_uses_small_t` = `tokens ∈ [1,6]` (`small_t.cu:228`), а T=7..16
идёт в `ChunkedSmallT` с полным перезапуском split-KV прохода на каждые 6 строк
(`causal_softmax_attention.cpp:288-303`): T=7 читает весь KV **дважды**, T=13 — трижды.
Для 27B (`q_heads == 24`) условие на `ChunkedSmallT` (`:331`, `q_heads == 16`) не выполняется, и
T=7..16 уходит в `Prompt`, у которого сетка `(ceil(T/64), QHeads)` = **24 CTA без split-KV**
(`prompt.cu:35-40`, `prompt_common.cuh:21`), где каждая из 6 Q-голов группы читает один и тот же
KV → шестикратная амплификация и 14 % занятых SM.
Ограничитель — `static_assert(TokenTile <= 6)` и `RowTiles <= 3` (`small_t_i8.cuh:88, 90`).
Для 27B (GroupSize 6) T=8 даёт 48 строк = **те же RowTiles=3**; для 35B (GroupSize 8) T=7..8
требует RowTiles=4, что совместимо с `Wc % RowTiles == 0` при Wc=8 и с
`PVNtPerWarp = 256/(2×8) = 16` (`static_assert` на `:92`). У XQA та же болезнь
(`T/mha.cu:2896-2897`), только шаг блока `M_TILESIZE`=32 вместо нашего 6 — то есть наши три
row-tile в одном CTA лучше, но их порог выше.

**Ожидаемый эффект.** В текущей рабочей точке (mtp3 = T=4, один кусок) — нулевой. Ценность
косвенная: при 32k на 35B лишний проход стоит 193 мкс на раунд, и в модели раунда
`13.78 + 0.180×колонок + 0.590×шагов` коэффициент 0.180 мс на колонку подозрительно близок к
0.193 мс = стоимости одного полного перечитывания KV при 32k. **Гипотеза: коэффициент при
колонках частично состоит из этого удвоения**, и её стоит проверить, прежде чем считать
направление «адаптивное окно» закрытым.

**Чем меряем.** Замер декодного внимания при T = 5, 6, **7**, 8 на S = 32k: если стоимость между
6 и 7 прыгает вдвое — гипотеза подтверждена. Затем A/B `TokenTile=8` против `ChunkedSmallT`.

**Риски.** RowTiles=4 поднимает `ProducerThreads` до 128 и уменьшает `VLoaderThreads`;
`q_s[Br*D]` растёт с 12 КБ (Br=48) до 16 КБ (Br=64) — при `MinBlocksPerSm=2` бюджет ещё есть,
но `DynamicArena`-маршрут (`small_t.cu:171-172`, Bc=64, 32 КБ динамики) может перестать
помещаться. Побитовость для T≤6 не затрагивается.

**Объём.** 3-4 файла + маршрутизация, ~150 строк.

### 8. Нормировать частичный аккумулятор перед записью

**Механизм.** XQA делит аккумулятор на **свой** `globalRowSum` до конверсии в fp16
(`T/mha.cu:2509-2524`) и умножает обратно при слиянии (`:2682`). Мы пишем ненормированный
аккумулятор в bf16 (`small_t_i8.cuh:641`). При одинаковых байтах нормированное значение лежит в
узком диапазоне около 1, то есть bf16 тратит все 8 бит мантиссы на полезное, а не на экспоненту
разброса между сплитами.

**Ожидаемый эффект.** Нулевой по скорости, **положительный по точности** при том же формате
частичных сумм. Ценность — как страховка, если кандидаты 2 или 4 (которые увеличивают число
сплитов или меняют их разбиение) покажут просадку точности.

**Чем меряем.** Только точностная батарея; скорость не должна двигаться (один `__frcp_rn` на
строку в partial-ядре и одно умножение в редукторе).

**Риски.** Вывод не побитов. Деление на `l0`, которое может быть нулём в вырожденном сплите —
нужен тот же guard, что уже стоит в редукторе.

**Объём.** 2 файла, ~30 строк.

## Опровергнуто / не переносится

- **Кеширование индексов страниц в smem — у нас уже лучше всех.** FlashInfer перестраивает
  `kv_offset_smem` раз в `bdx` итераций внутри цикла (`FI/decode.cuh:525-534`), XQA дозагружает
  регистровый вектор `KCachePageIndices` каждый CTA-тайл (`T/mha.cu:1772-1786`, `:1868-1877`),
  мы читаем все индексы сплита один раз до цикла (`small_t_i8.cuh:205-207`). Заимствовать нечего.
- **`uint_fastdiv` для размера страницы** (`FI/decode.cuh:485`) нужен только потому, что
  FlashInfer поддерживает произвольный `page_size`. У нас 64 = `1 << 6`, деление уже сдвиг.
- **Скалярный декод FlashInfer** (`FI/decode.cuh:64-115`) — шаг назад: у нас QK на int8-MMA и
  PV на bf16-MMA. Заодно фиксирую расхождение с брифом: пункт «тензорные ядра в декодном
  внимании (118.4 против 119.0 мкс)» относится к соседнему движку; в NInfer декодные ядра
  **тензорноядерные уже сегодня** (`small_t_i8.cuh:441, 600`, `small_t_fp8.cuh:389`), и имена
  ядер это фиксируют (`..._tc_partial_bf16_kernel`).
- **Fused split-K reduction через глобальный семафор (`T/mha.cu:2616-2718`)** — механизм
  реальный и убирает второй запуск ядра, но для нас несовместим с CUDA-графом декода: семафоры
  надо обнулять между реплеями (у XQA это решает `atom.inc` с wrap, но там нет графа с
  переменным `nbSubSeqPerSeq`), а «последний CTA сливает» вводит зависимость от порядка
  планирования, из-за которой сумма по сплитам перестаёт быть воспроизводимой между запусками.
  Кандидат 3 берёт большую часть выигрыша без этих последствий.
- **`reorder16bQHeadsToMatch8bKCache`** (`T/mha.cu:1904-1912`) — трюк, переносящий стоимость
  перестановки под распаковку fp8-K с «каждый тайл» на «раз на ядро». Нам не нужен: мы K вообще
  не деквантуем (int8 идёт прямо в `mma_s8`, fp8 — прямо в `mma_fp8_e4m3`).
- **Пер-тензорный масштаб KV, вложенный в `qkScale`/`voScale`** (`T/mha.cu:1756-1757`,
  `:2520-2522`) — предельный случай «экономии на масштабах»: ноль байт метаданных и ноль работы
  в цикле. Для нас неприменим: один скаляр на весь KV-кеш при head_dim 256 и длинном контексте
  сведёт int8 к бессмысленной точности; наш выбор группы 64 сделан именно против этого.
- **Warp specialization 1 IO + 8 math (FlashMLA sm120,
  `FI/sparse_mla_sm120/decode_dsv3_2_kernel.cuh:44-52`)** — бриф уже фиксирует регрессию;
  к тому же у нас продюсер/консьюмер-раскладка есть, только по другой оси (продюсер = row-tile).
- **`cp.async.bulk` / TMA для страничного KV** (`FI/sparse_mla_sm120/common/kv_cache_io.cuh:73-91`,
  `T/mla_sm120.cu:166-171`) — прямо в списке опровергнутого.
- **Глубокий `cp.async`-конвейер в partial-ядре.** XQA держит 2 буфера K/V (`T/mha.cu:120-123`)
  — то же, что у нас; глубина 12 есть только в sm_120-родном MLA (`T/mla_sm120.cu:336`), где
  запись KV в 656 Б на токен и другой бюджет smem. У нас углубление до 2 арен требует +16 КБ
  smem (сейчас `4*Bc*D` = 32 КБ при Bc=32), что при `MinBlocksPerSm = 2` не оставляет места;
  бриф фиксирует −9..15 % на глубоких конвейерах. Не предлагаю.
- **Разреженность по top-k индексам** (`FI/sparse_mla_sm120/common/kv_cache_io.cuh:74-79`) и
  `skip_softmax_threshold_scale_factor` (`flashinfer/flashinfer/decode.py:3348-3352`) —
  ThriftAttention-класс, закрыт.
- **Формула сплитов FlashInfer в чистом виде не переносится**: пол в 256 ключей на кусок
  (`FI/decode.cuh:713`) разумен для batch ≫ 1; у нас при S ≤ 4096 используется 32 ключа на сплит
  (`small_t.cuh:84`), и их пол оставил бы машину пустой при concurrency 1. Переносится не
  формула, а её **монотонность** (кандидат 2). То же и у XQA — его потолок
  `SM/(batch*nbKHeads)` при batch=1 и 2 KV-головах даёт 85 сплитов, то есть **половину нашего**,
  потому что у него 1 CTA на SM, а у нас 2.
- **SWAP_AB для спекуляции** (`T/mha_sm90.cu:43-58`) — только sm_90 (`jit/xqa.py:48-50`),
  и смысл его в том, чтобы GMMA с M=64 не пропадала при малом числе строк. У нас MMA m16, и при
  T=1 на 35B заполнено 8 строк из 16, на 27B — 6 из 16; но ядро memory-bound с запасом ×9,
  так что борьба за строки MMA ничего не даст. Не переносим.
- **`createpolicy` / L2-подсказки на поток KV** — в XQA этого **нет**, есть только
  закомментированный `L2::128B` (`T/ldgsts.cuh:28`, «prefetch makes it slower on sm_86») и два
  открытых TODO (`T/mha.cu:1954`, `T/mhaUtils.cuh:113`). То есть у NVIDIA это неоплаченный долг,
  а не готовый механизм; заимствовать нечего, и `applypriority` на sm_120a всё равно знает
  только `.evict_normal` (бриф).
- **Иерархии страниц, сжатия KV, разных размеров страниц нет ни в одном ядре корпуса.**
  Единственный механизм длинного контекста помимо split-KV — sliding window
  (`T/mha.cu:1714-1730`), который у нас есть отдельным ядром
  (`src/ops/softmax_attention/sliding_window/`).
- **PDL** (`T/defines.h:147-149`) — в списке опровергнутого; вдобавок форк FlashInfer сам
  снижает его на sm_120 до наивного (`F/defines.h:132-143`).

## Открытые вопросы

1. **Какова фактическая доля пика HBM у нас на 200k?** Арифметика даёт нижнюю границу 1.18 мс
   (35B) и 3.69 мс (27B) на шаг. Заявленная в отчёте деградация 216 → 157 ток/с — это +1.74 мс
   на токен; при mtp3 (≈2.5-3 токена на раунд) чисто-KV предсказание даёт ≈0.4-0.5 мс на токен
   для 35B, то есть расхождение ×3.5. Либо цифры отчёта относятся к 27B, либо в длинном
   контексте есть вторая статья расходов. Это надо развести измерением прежде, чем оценивать
   любой кандидат на 200k.
2. Захвачен ли редуктор в тот же CUDA-граф, что и partial-ядро (`src/core/decode_graph.cpp`)?
   Если да — вариант 3b (смена сетки) дороже, чем кажется.
3. Ни один источник в корпусе не даёт цифр точности для NVFP4-KV. FlashInfer его собирает и
   выставляет наружу (`jit/xqa.py:73-80`), но качество не документирует. Ответ придётся получать
   своим стендом; это главный риск кандидата 1.
4. Почему тиры в `causal_small_t_default_splits` выбраны именно 64/128/256/480 ключей — были ли
   они измерены на монотонной сетке или подобраны по точкам? Если второе, кандидат 2 может
   оказаться возвратом к уже отвергнутой конфигурации; в замере надо покрыть середины тиров,
   а не только границы.
5. Как спецслучаи T=5/6 (`small_t.cuh:101-115`, `small_t.cu:54-69`, окна 128/160/512/5000/8198)
   взаимодействуют с монотонной огибающей, если её включить? Проверить, что огибающая не
   перекрывает измеренные спецточки.
6. `ctaTile.x = 256` у XQA против нашего `Bc = 32`: их CTA берёт 256 токенов KV за итерацию
   при 1 CTA на SM, наш — 32 при 2 CTA на SM. При равном числе байтов в полёте это разные
   компромиссы по smem и по гранулярности сплита; какой из них лучше на 5090, из кода не следует.
