# V6 — выходной тракт: голова модели, логиты, сэмплинг

## Что это за механизм

Выходной тракт всех четырёх чужих движков устроен одинаково по структуре и отличается только
степенью слияния: последнее скрытое состояние собирается по последней позиции каждой
последовательности → плотный GEMM на весь словарь → **полная материализация `[строк, V]`** →
цепочка фильтров (штрафы, температура, top-k, top-p, min-p) → сэмплинг. **Ни один из четырёх
не сливает проекцию на словарь с argmax или top-k, ни один не считает top-k до материализации
логитов, ни один не урезает словарь целевой головы.** Единственное настоящее сокращение
словаря во всём корпусе — черновая голова EAGLE-3 с таблицей `d2t` (vLLM, SGLang, TokenSpeed,
TensorRT-LLM) и наш `draft_head` на 131072 строки. То есть в этой ячейке **мы не отстаём —
мы впереди по двум пунктам сразу** (у нас голова квантована, а у них bf16/fp32; у нас
стохастический приём работает с урезанной черновой головой, а у TensorRT-LLM это запрещено
исключением).

Зато арифметика показала то, чего кампания не считала: **выходной тракт — это 15.6 % байт
весов на токен в обычном декоде 35B и ~19–27 % байт раунда mtp3**, потому что черновая голова
читается **три раза за раунд** (по одному разу на каждый шаг чернового авторегресса).

### Наш тракт по шагам

- `ninfer/src/targets/qwen3_6/impl/runtime/text_prefill_impl.h:131-147` — `sample_from_hidden`:
  в префилле голова применяется **только к последнему скрытому состоянию** `[hidden,1]`.
  Логиты по всем позициям префилла не считаются никогда. (Это ровно та экономия, которую
  TensorRT-LLM считает главной на выходном пути.)
- `ninfer/src/targets/qwen3_6/impl/runtime/decode_impl.h:39-44` — обычный декод:
  `ordinary_decode_batch` → `ops::sample`. Промежуточного argmax нет.
- `ninfer/src/targets/qwen3_6/impl/runtime/text_context_impl.h:743-745` — верификация:
  `rmsnorm` → `ops::linear(hidden, *lm_head_, flat_logits)` → `ops::argmax(...)`.
  Логиты `BF16 [248320, width, batch]`.
- `ninfer/src/targets/qwen3_6/impl/runtime/text_context_impl.h:558-575` — `proposal_argmax`.
  При `proposal_head_ != nullptr`: `work_.alloc(BF16, {131072, T})` → `ops::linear` по
  черновой голове → `ops::argmax` → `ops::proposal_remap_token_ids`. Иначе — **полная
  Q6-голова на 248320 строк ради одного argmax**.
- `ninfer/src/ops/kernel/speculative_round.cuh:566-573` — `proposal_remap_token_ids_kernel`:
  один поток на предложенный токен, `tokens[i] = id_map[tokens[i]]`. Цена отображения —
  O(batch·k) обращений по 4 байта, то есть ноль.
- `ninfer/src/targets/qwen3_6/impl/runtime/mtp_impl.h:166-189` — **черновая голова читается
  `k` раз за раунд**: один `mtp_propose_batch` до цикла и `k-1` внутри. При mtp3 это 3 чтения.
- `ninfer/src/targets/qwen3_6/impl/runtime/speculative_target_impl.h:27-31` —
  `speculative_accept_greedy_drafts` после argmax.

### Наш сэмплер

- `ninfer/src/ops/kernel/sampling.cuh:106-158` + `:160-295` — двухступенчатый маршрут:
  `sampling_partial_topk_kernel` (по одному CTA на плитку из 512 токенов словаря, CUB
  `BlockMergeSort` до `cap` кандидатов) и `sampling_group_finalize_sample_kernel`
  (слияние групп по 25 плиток, затем финальное слияние). **Один проход по словарю, полной
  сортировки нет, полный softmax не материализуется.** По устройству это ровно то, к чему
  vLLM пришёл в «v2» и что TokenSpeed называет QRITA, только у нас потолок кандидатов
  фиксирован.
- `ninfer/src/ops/common/sampling_workspace.h:24-25` — `kSamplerFastCandidates = 20`,
  `kSamplerCandidateCap = 20`.
- `ninfer/include/ninfer/ops/sampling.h:60-64` и `ninfer/src/serve/serve_options.cpp:300` —
  **`top_k` жёстко ограничен 20, и `top_p` считается только по этим 20 кандидатам.**
- `ninfer/src/ops/kernel/sampling_device.cuh:137-149` — `sampling_adjusted_logit`: presence и
  frequency штрафы **вшиты в тот же проход по словарю**, что и отбор кандидатов; при нулевых
  штрафах ветка не исполняется и `token_counts` не читается.
- `ninfer/src/ops/kernel/sampling_device.cuh:190-223` — `sampling_normalize_support`: min_p,
  top_p, ренормировка и обратная CDF — всё на **одном потоке** по ≤20 кандидатам.
- `ninfer/src/targets/qwen3_6/impl/runtime/program_impl.h:10606-10609` — `token_counts`
  привязывается к лейну только когда штрафы ненулевые, иначе `nullptr`.
- `ninfer/src/targets/qwen3_6/impl/runtime/layouts_impl.h:242-244` — `token_counts`
  `I32 [248077, max_concurrency]` = 992 КБ на запрос.
- `ninfer/src/ops/kernel/speculative_round.cuh:91-111` и `:349-368` — жадный приём без штрафов:
  сравнение `row_targets[a] == row_drafts[a]` по уже посчитанным argmax-ам, **ноль
  дополнительных проходов по словарю**.
- `ninfer/src/ops/kernel/speculative_round.cuh:198-241` — стохастический приём: черновик
  жадный, значит q одноточечное, и тест сводится к `u < p_i(drafts[i])` по усечённому
  распределению цели; при отказе — `sampling_pick_from_support(..., exclude=d, ...)`.
  **Вероятности черновика не нужны вообще.**
- `ninfer/src/ops/kernel/target_logprobs.cuh:41-67` — логпробы: двухпроходный logsumexp,
  один CTA на колонку, на выход только логпроба целевого токена. Полный `[V]` log-softmax
  не материализуется.

### Как выбрана наша черновая голова (и что уже измерено)

- `ninfer/docs/maintainer/qwen3.6-35b-a3b-artifact.md:564-582` — 131072 строки отбираются по
  **убыванию частоты по корпусу** плюс принудительный набор спец-токенов, затем те же строки
  `lm_head.weight` квантуются в Q4. То есть это частотный отбор словаря, а не обучение.
- `ninfer/tools/freq_corpus/fixtures/ranking/coverage.accept.report.json` — **сетка покрытия
  уже посчитана** для 1024…131072 строк, на трёх выборках, с разбивкой по доменам.
  Покрытие на принятых токенах (`accept:heldout`, total / худший домен):
  32768 → 91.68 % / 82.74 %; 49152 → 94.58 % / 88.07 %; **65536 → 96.31 % / 91.46 %**;
  **98304 → 98.23 % / 95.60 %**; **131072 → 99.19 % / 97.86 %**.
- `ninfer/include/ninfer/types.h:77` — **`ProposalHead::Full` — умолчание**; оптимизированная
  голова включается флагом `--lm-head-draft`
  (`ninfer/src/serve/serve_options.cpp:284-285`, `ninfer/apps/cli/options.cpp:141-142`).
- Но: `ninfer/tools/bench/run_ninfer_bench_matrix.py:68`,
  `ninfer/tools/bench/run_serve_concurrency.py:319`, `ninfer/docs/performance.md:56` —
  **все наши стенды флаг ставят**. То есть 579 tok/s снято с оптимизированной головой,
  и «включить флаг» бесплатным выигрышем в бенчмарке не будет; это дефолт для пользователя,
  а не для замера.

## Что у нас сегодня

Сведено выше по разделам; коротко по пунктам задания.

1. **Тракт.** Префилл: `linear(последний hidden, output_head)` → `sample`
   (`text_prefill_impl.h:131-147`). Обычный декод: `linear` → `sample`
   (`decode_impl.h:39-44`). Верификация: `linear` → `argmax` → `accept`

   Буферы: `target_logits BF16 [248320, k+1, batch]`, `proposal_logits BF16 [248320, batch]`,
   рабочий `BF16 [131072, T]` (`round_state.cpp:150-159`, `layouts_impl.h:343-347`).
2. **Квантование головы.** 35B — Q6G64_F16S, 27B (Qwen38Nvfp4) — FP8 row-scale,
   27B (Qwen36GroupwiseInt) — Q6G64_F16S. Отдельного «декодного» маршрута нет: выбор
   ядра идёт по T (`q6_dispatch.cpp:24-42`: T≤3 → SIMT-маршрут `r8_c4`, T≤16 → `mma_r64_c16_k128`
   и далее). Для NVFP4 маршрута на форму `[248320, K]` **нет** (`nvfp4_dispatch.cpp:31-38`).
3. **Сколько раз трогаются логиты за раунд mtp3** (batch 1, k=3, ширина 4):
   целевые логиты пишутся 1 раз (1.99 МБ), читаются argmax-ом 1 раз (1.98 МБ) и ещё
   `extent+1` раз в приёме **только если** temperature>0 или включены штрафы;
   черновые логиты — 3 записи и 3 чтения по 0.26 МБ. Итого ≈ 5.5 МБ при жадном режиме.
   **Сливать тут нечего: это 0.7 % байт выходного тракта.** Единственная реальная
   мёртвая работа — `ops::argmax` в `text_context_impl.h:745` вызывается безусловно, а
   `target_tokens` потребляется только жадной веткой приёма (`speculative_round.cuh:96`,
   `:355`); в стохастическом режиме это 1.98 МБ впустую = 1.1 мкс.
4. **Чужие** — см. раздел выше.
5. **Черновая голова меньше словаря** — есть, 131072 из 248077 (52.8 %), отбор частотный,
   отображение — один gather по id (бесплатно), токены вне чернового домена просто не могут
   быть предложены (корректность держит цель). Сетка покрытия уже посчитана и лежит в репозитории.
6. **Логпробы и штрафы** — штрафы слиты в проход отбора кандидатов, min_p/top_p/ренормировка
   идут по ≤20 кандидатам одним потоком, логпробы — двухпроходный logsumexp без материализации.
   `repetition_penalty` (мультипликативный), `logit_bias`, `allowed_token_ids` и маска
   грамматики у нас **отсутствуют** — не проверено, нужны ли.

## Кандидаты для NInfer

### 1. Ослабленный приём черновика (`mtpRelaxedAcceptance`), включаемый только внутри блока размышления

**Механизм.** Сегодня жадный приём требует точного совпадения `target_argmax[i] == draft[i]`
(`speculative_round.cuh:96`). TensorRT-LLM принимает черновой токен, если он входит в top-K
цели и его значение отстоит от top-1 не более чем на `delta`
(`trtllm/cpp/tensorrt_llm/kernels/speculativeDecoding/mtpKernels.cu:489-502`), причём
послабление **вооружается и разоружается по токенам начала/конца размышления**
(`:523-543`). У нас это почти ничего не стоит реализовать, потому что
`speculative_sampling_partial_topk_kernel` уже умеет строить top-`cap` со значениями за
**один** проход по словарю (`ninfer/src/ops/kernel/speculative_round.cuh:262-320`) — в
жадном режиме он просто схлопывает `cap` до 1 (`:288`). Достаточно в новом режиме поставить
`cap = relaxed_top_k` (≤20, потолок уже есть) и заменить тест приёма; `ops::argmax` в
`text_context_impl.h:745` в этом режиме становится избыточным и снимается.

**Ожидаемый эффект.** Байт почти не добавляется: один лишний полный проход по целевым
логитам — 4 колонки × 496 КБ = **1.98 МБ на раунд = 1.1 мкс при пике = 0.05 % раунда**
(и он компенсируется снятым argmax-ом того же объёма). Выигрыш весь на стороне
принимаемых токенов: при k=3 ожидаемое число токенов за раунд равно `1+p+p²+p³`;
рост per-draft приёма с 0.75 до 0.82 даёт 2.734 → 2.933 токена, то есть **+7.3 % tok/s
при неизменной цене раунда**. Это единственный кандидат в ячейке, у которого потолок
двузначный.

**Чем меряем.** Канонический стенд (`tools/bench/run_ninfer_bench_matrix.py`, чанк 8192,
`--spec mtp --draft-tokens 3 --lm-head-draft`), два прохода. A/B: `relaxed_top_k=0`
(текущее поведение) против `relaxed_top_k ∈ {2,4,8}` × `delta ∈ {0.05, 0.1, 0.2}` в
логитном или в вероятностном пространстве по top-20 support. Обязательная вторая половина —
батарея точности (AIME25 и перплексия), потому что механизм **меняет вывод**. Отдельно
снять `accepted_per_position` (`program_impl.h`, `SpeculativeStats`), чтобы отделить рост
приёма от шума.

**Риски и что ломается.** Побитовость вывода теряется — это не «регрессия», а именно
предмет замера; заметка «MTP parity tax» и так фиксирует, что mtp3 повторяет вывод mtp0
только на 2 из 12 промптов. Гейтирование по размышлению **не сохраняет ответ**: изменённое
рассуждение меняет и ответ; оно лишь сужает поверхность риска на более избыточный текст.
Состояние размышления у нас живёт на хосте (`frontend.cpp:1257-1264`, `OutputSession`),
а `SamplingConfig` и так копируется в ингресс каждый раунд
(`mtp_impl.h:81-83`), так что проводка бесплатна и графозахват не ломается.
Регистровое давление: `cap` 1→8 в `speculative_sampling_partial_topk_kernel` включает
CUB-сортировку вместо максимума — путь уже скомпилирован для стохастического режима,
новых занятостей не появляется.

**Оценка объёма.** ~6–8 файлов: `include/ninfer/ops/sampling.h` (+2 поля в `SamplingConfig`),
`src/ops/kernel/speculative_round.cuh`, `src/ops/launcher/speculative_round.cu`,
`src/targets/qwen3_6/impl/runtime/{text_context_impl.h, speculative_target_impl.h,
program_impl.h}`, `src/serve/serve_options.cpp`, `apps/cli/options.cpp`.

### 2. Сузить черновую голову с 131072 до 98304 или 65536 строк

**Механизм.** Ничего нового изобретать не надо: конвейер отбора уже описан
(`docs/maintainer/qwen3.6-35b-a3b-artifact.md:564-582`), сетка покрытия уже посчитана
(`tools/freq_corpus/fixtures/ranking/coverage.accept.report.json`), а размер головы —
единственная константа (`variant.h:36`, `bindings.cpp:297-298`). 131072 = 2¹⁷ выглядит
выбранным как круглое число, а не как оптимум по времени раунда.

**Ожидаемый эффект.** 35B: 98304 строк → 107.0 МБ вместо 142.6, ×3 = **−106.9 МБ на раунд**
(−2.3…−3.4 % байт раунда); 65536 строк → 71.3 МБ, ×3 = **−213.9 МБ** (−4.5…−6.9 %).
27B: 98304 → **−267 МБ на раунд** (−1.3 %); 65536 → **−535 МБ** (−2.5 %).
Плата — покрытие принятых токенов падает с 99.19 % до 98.23 % (98304) или 96.31 % (65536);
на худшем домене — с 97.86 % до 95.60 % / 91.46 %. Через модель раунда `1+p+p²+p³`
это −1.1 % и −3.3 % принятых токенов соответственно, то есть **чистый итог ≈ +2 % (98304)
и ≈ +3.4 % (65536) на 35B**, и заметно меньше на 27B. Дополнительная гипотеза, которую
стоит проверить тем же замером: при 65536 строках голова 35B — **71.3 МБ, что меньше
96 МБ L2**, и второй/третий черновые шаги раунда могут читать её из L2, а не из HBM;
между шагами проходит только тело MTP (~69 МБ), так что вытеснение частичное.

**Чем меряем.** Пересборка артефакта с уменьшенной головой (шаг 12.5 конвейера), затем
тот же канонический стенд, два прохода, плюс `accepted_per_position` и батарея точности.
Точка сравнения — не «tok/s против tok/s», а **произведение (время раунда) × (принятых
токенов)**, потому что двигаются оба множителя. Отдельно замерить L2-гипотезу: раунд
с 65536 против раунда с 98304 должен дать сверхлинейный выигрыш, если L2 работает.

**Риски и что ломается.** Побитовость **сохраняется** — черновик только предлагает, приём
у цели не меняется; меняется лишь скорость. Ломается совместимость артефакта
(`validate_draft_ids`, `bindings.cpp:276-292`, ждёт ровно 131072). Регрессия на редких
языках и редких токенах сильнее, чем в среднем: худший домен `other_chat` теряет
6.4 п.п. при 65536.

**Оценка объёма.** 3–4 файла в движке (`variant.h`, обе `bindings.cpp`, `argmax.cu:19`
`kShortlistRows`) плюс офлайн-пересборка артефакта.

### 3. Перевести голову 27B (профиль Qwen38Nvfp4) с FP8 row-scale на Q6G64_F16S

**Механизм.** `endpoint_format(Qwen38Nvfp4)` возвращает `FP8_E4M3FN_ROW_BF16S`
(`qwen3_6_27b/impl/load/bindings.cpp:42-43`), то есть **1 байт/вес — самая слабо сжатая
матрица в модели**, где MLP лежит в NVFP4 (0.5625 Б/вес). При этом маршрут Q6 на ровно эту
форму **уже скомпилирован**: `q6_dispatch.cpp:10-23` обрабатывает `k=5120, n=248320` со
всеми плитками, и профиль `Qwen36GroupwiseInt` его уже использует.

**Ожидаемый эффект.** 1271.9 → 993.3 МБ = **−278.6 МБ на каждую верификацию**
(−21.9 % головы), при пике HBM это **−155.5 мкс**. На фоне раунда 27B в ~21.3 ГБ это
**−1.3 %**. Если дополнительно взять Q4 (маршрут `q4_dispatch.cpp:40,49` знает `n=131072`,
но не `248320` — нужен новый), было бы 675.4 МБ, то есть −596.5 МБ = −2.8 % раунда.

**Чем меряем.** Пересборка артефакта 27B с Q6-головой; A/B на канонической точке 27B
(`--spec mtp --draft-tokens 3 --lm-head-draft`), два прохода; перплексия и AIME25
обязательны, потому что голова прямо определяет токен. Ориентир по точности есть: 35B
уже живёт с Q6-головой.

**Риски и что ломается.** Q6 — программный dequant, что противоречит установке 27B-профиля
«no software dequant»; но при M=1..4 голова полностью упирается в HBM, а не в MMA, так что
цена dequant-а прячется. Побитовость вывода 27B теряется (другие веса — другие логиты).
Точность головы — главный риск; Q6 при группе 64 даёт 6.25 бит/вес против 8 у FP8.

**Оценка объёма.** 2 файла (`qwen3_6_27b/impl/load/bindings.cpp` — `endpoint_format` и
две привязки) плюс офлайн-пересборка артефакта. Ядро уже есть.

### 4. Точный большой `top_k` без сортировки (QRITA), как закрытие семантического долга

**Механизм.** У нас `top_k` жёстко ≤20 и `top_p` считается по этим 20 кандидатам
(`sampling_workspace.h:24-25`, `include/ninfer/ops/sampling.h:60-64`,
`serve_options.cpp:300`). Это значит, что при `top_p=0.95` и высокой энтропии наше ядро
усекает ядро распределения там, где vLLM/SGLang/TokenSpeed его не усекают, и наши числа
точности при «одинаковых параметрах сэмплинга» сравнимы с чужими только условно.
TokenSpeed решает это без сортировки: оценка порога по среднему и дисперсии строки через
таблицу гауссовых процентилей, компактизация выбросов и **троичный поиск точного k-го
порога** (`tokenspeed-kernel/.../triton/topk_topp.py:599-783`, ≤18 итераций по компактному
буферу, `:944-958` — то же для top_p).

**Ожидаемый эффект.** На скорость — **нулевой или отрицательный**; это кандидат на
корректность, а не на производительность. Ценность в том, что он снимает оговорку с
любого сравнения точности с чужими движками и открывает `top_k` > 20 и точный `top_p`
как режим.

**Чем меряем.** Не бенчмарком, а сравнением распределений: при фиксированном seed и
`top_p=0.95, temperature=0.7` доля позиций, где истинное ядро шире 20 токенов, на нашем же
корпусе; затем разница в AIME25/перплексии между усечённым и точным top_p.

**Риски и что ломается.** Меняется вывод при `top_p<1` на высокоэнтропийных позициях.
Троичный поиск даёт данные-зависимое число итераций — это плохо ложится на графозахват
декода (`decode_graph.cpp`), нужен фиксированный потолок итераций.

**Оценка объёма.** 3–4 файла, всё внутри `src/ops/{kernel,launcher}/sampling*` плюс снятие
проверки в `serve_options.cpp:300`.

## Опровергнуто / не переносится

- **Слияние проекции на словарь с argmax/top-k — этого нет ни у кого.** Проверено во всех
  четырёх: vLLM (`logits_processor.py:139-178` → `sampler.py:97`), SGLang
  (`logits_processor.py:749-750`), TokenSpeed (`logits_processor.py:640-641`), TensorRT-LLM
  (`modules/logits_processor.py:33-34`). Единственное приближение — TP-локальный argmax
  (`vllm/model_executor/layers/logits_processor.py:189-239`,
  `tokenspeed/runtime/layers/logits_processor.py:657-671`), и он экономит **коммуникацию
  между рангами**, а не байты HBM; при TP=1 вырождается в обычный argmax. Вне области брифа.
  Считать это и не стоит: у нас логиты в BF16 занимают 496 КБ на колонку против 397 МБ
  весов головы — слияние экономило бы **0.13 %**.
- **Урезание словаря целевой головы (vocab pruning, иерархический софтмакс, частотный отбор)
  — нет ни у кого.** Целевые прогоны везде идут по полному V; поиск по `hierarchical.softmax`,
  `adaptive.softmax`, `prune.vocab`, `frequency.based` даёт ноль во всех четырёх клонах.
  Частотный отбор словаря существует **только** для черновой головы — и он у нас уже есть,
  причём в более сильном виде: SGLang режет строки той же bf16-головы в рантайме
  (`eagle_worker_v2.py:315`), а мы отобранные строки ещё и переквантовываем в Q4.
- **Расширение черновых вероятностей до целевого словаря (`d2t` scatter) — нам не нужно и
  переносить нечего.** vLLM аллоцирует `[B, V_target]` и заливает `-inf` на каждом черновом
  шаге (`llama_eagle3.py:337-357`), TensorRT-LLM держит нулевой
  `float32[max_num_requests, max_draft_len, vocab_size]` (`interface.py:657-664`) и всё равно
  запрещает `d2t` со стохастическим сэмплингом (`sampler.py:1411-1421`). У нас черновик
  всегда жадный, значит q одноточечное, тест приёма сводится к `u < p(d)`, и черновые
  вероятности не нужны вообще (`speculative_round.cuh:198-241`). **Наша конструкция строго
  лучше — это стоит зафиксировать, а не заимствовать.**
- **Верификация сравнением id (TokenSpeed `verify.py:34-63`)** — ноль проходов по словарю,
  но **не сохраняет распределение**: у них нет члена с вероятностью черновика. У нас жадная
  ветка приёма и так стоит ноль проходов (`speculative_round.cuh:91-111`), а стохастическая
  ветка распределение сохраняет. Брать нечего, отдавать точность не за что.
- **Слитый кернел штрафов (vLLM v2 `penalties.py:106`, TokenSpeed `penalties.py:34`)** —
  у нас штрафы уже вшиты в тот же проход по словарю (`sampling_device.cuh:137-149`), причём
  ещё и с корректным round-local overlay для спекулятивных колонок (`:129-136`). Их
  битово-упакованная маска присутствия (`vllm/v1/worker/gpu/sample/penalties.py:32-37`,
  31 КБ вместо 992 КБ) сократила бы наш проход со штрафами с 1.49 МБ до 0.53 МБ на колонку.
  При 397 МБ весов головы это **0.24 % раунда**. Механизм настоящий, выигрыш — шум.
  Не кандидат.
- **`_compute_local_logits_stats_kernel` (vLLM v2, `rejection_sampler_utils.py:193`)** —
  один проход выдаёт argmax + max + sumexp сразу. Красиво, но экономит нам ровно один
  проход по 1.98 МБ логитов за раунд = **1.1 мкс = 0.03 %**. Не кандидат.
- **Хостовые проверки «не запускать ядро вовсе»** (`trtllm penalties.py:829-880`,
  `vllm/v1/worker/gpu/sample/states.py:77-98`) — нам недоступны по конструкции: декод
  захвачен в CUDA-граф (`src/core/decode_graph.cpp:63,111,144`), а `SamplingConfig` читается
  ядром из устройственной памяти (`sampling.cuh:22`), так что хост не может решить, пускать
  ли запуск. Пустые CTA у нас и так выходят по первой же проверке
  (`speculative_round.cuh:274`) без чтения логитов. Не переносится, и не нужно.
- **Параметры сэмплинга в устройственных пулах по слоту запроса (TokenSpeed
  `backends/triton.py:107-120`, `base.py:194-203`)** — у нас функционально то же самое и

## Открытые вопросы

1. **Достигает ли чтение головы пика HBM?** Вся арифметика выше — «при 1792 ГБ/с». При
   T=1..3 на 35B выбирается SIMT-маршрут `launch_q6_simt_r8_c4` (`q6_dispatch.cpp:26`),
   при T=4 — MMA-плитка на 16 колонок (`:27`), из которых 12 холостые. Достигнутая доля
   пика для обеих форм не измерялась; без неё выигрыш от сжатия головы масштабируется
   неизвестным коэффициентом. Замер: отдельный операторный прогон головы на T ∈ {1,2,3,4,8}
   с учётом заметки об этаже частоты (`ninfer-operator-bench-clock-floor`).
2. **Сколько уникальных экспертов активно при ширине 4 в верификации?** От этого зависит
   знаменатель во всех долях раунда 35B (разброс 3.11–4.72 ГБ). Число известно движку
   в рантайме, но в клоне нигде не логируется.
3. **Какой `relaxedDelta` и в каком пространстве.** TensorRT-LLM сравнивает вероятности
   после softmax (`mtpKernels.cu:489-502` работает с `topKValue`, полученными из
   `mtp.py:676-679` после полного softmax). У нас на этом месте нормировка по 20 кандидатам
   (`sampling_device.cuh:190-223`), то есть «delta» в другом пространстве. Эквивалентность
   не выведена; для A/B её надо либо доказать, либо мерить обе формы.
4. **Какое покрытие черновой головы нужно на самом деле.** Сетка в
   `coverage.accept.report.json` даёт покрытие *позиций*, а не приём *цепочки*. Связь
   «−1 п.п. покрытия → −x п.п. приёма» в репозитории не измерена; модель `1+p+p²+p³`
   выше — предположение, а не факт.
5. **Есть ли у нас потребность в `repetition_penalty`, `logit_bias`, `allowed_token_ids`
   и маске грамматики.** У всех четырёх чужих это есть; у нас нет. Не проверено, требуется
   ли это по продуктовому контракту — но если потребуется, у TensorRT-LLM есть готовый
   ответ на то, как это делать без прохода по словарю: разреженный `index_put_` вместо
   плотной маски (`trtllm .../sampler/token_ban.py:556-568`) и битовая маска с d2t-адресацией
   (`cpp/tensorrt_llm/kernels/logitsBitmask.cu:185-230`).
