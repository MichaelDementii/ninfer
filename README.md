# pr_handoff — общая папка для подачи в `Neroued/ninfer`

Здесь лежит всё, что нужно, чтобы подать очередную заявку в апстрим, не спрашивая ни у кого
контекста: правила автора, готовые тексты, ветки в виде bundle, сырые числа кампаний и харнесс,
которым они сняты.

**Правило одно: сюда коммитится только то, что доведено до состояния «можно подавать завтра».**
Черновики и промежуточные замеры живут в рабочих папках, не здесь.

## Новое 2026-09-01: разбор чужих движков — [`РАЗБОР_чужих_движков/`](РАЗБОР_чужих_движков/)

Пока оба слота заняты, четырнадцать ячеек параллельно читали исходники **vLLM 0.28.0,
SGLang 0.5.18, FlashInfer, CUTLASS, TensorRT-LLM и TokenSpeed** — ровно тех версий, на которых
снят сторонний отчёт по 4× RTX 5090, — и сравнивали с нашим деревом. Пятнадцать полных разборов,
каждое утверждение со ссылкой `файл:строка`.

**Что это даёт напарнику: готовую очередь из двадцати с лишним кандидатов с арифметикой и планом
замера, и список закрытых направлений, куда можно не ходить.**

Коротко, что вскрылось:

- **Пять утверждений отчёта опровергнуты кодом.** «SGLang быстрее на префилле в 2.57×» — цена
  питоновского хоста, ядра у обоих движков буквально одни и те же. «fp8-KV даёт +43% префилла» —
  подмена бэкенда `FLASH_ATTN` → `FLASHINFER`. «Три GDN-бэкенда нейтральны» — резолвер vLLM на
  sm_120 возвращает `triton` для всех четырёх значений флага. И так далее.
- **Поправка к нашей картине: f16-накопления во внимании у нас нет и не было.** `mma_f16` — это
  `...f32.f16.f16.f32`, аккумулятор f32. PV сидит на ярусе ~257 TFLOPS при том, что занимает
  **80% тензорного времени** в int8-ядре и 67% в fp8-ядре. Три независимых чужих решения
  численного вопроса найдены; наше собственное плечо когда-то мерялось и давало **+4.3…9.2%**.
- **Выходной тракт — 18-27% раунда декода** на 35B, и кампания его до сих пор не считала.
  Голова в Q6 это 397.3 МБ = 15.6% байт весов на токен, черновая голова читается три раза за
  раунд. Самый дешёвый кандидат всей кампании: сузить черновую голову 131072 → 98304/65536,
  побитовость целевого вывода не страдает, сетка покрытия уже в репозитории.
- **Куда не ходить:** автор запушил `feat/kv-nvfp4-k8v4` 1 сентября в 19:05 (+0800). NVFP4
  KV-кеш он делает сам.
- **Про нас самих:** наш 27B-NVFP4 артефакт квантован **целиком unsloth** (конвертер копирует
  без переквантования) и даёт GPQA 90.40 против 87.37 у нашей int-сборки. Наш квантователь —
  RTN по absmax без калибровки.

Начинать читать с части III (очередь кандидатов) и части IV (что закрыто).

## Как устроена папка

```
00_rules/          правила автора и процесс подачи. Читать первым.
01_w8_rowsplit/    следующая заявка: тексты, bundle ветки, сырые данные, отчёт ревью
02..07_*/          остальные кандидаты по приоритету
90_harness/        скрипты кампании: две руки из одного build-каталога, отчёт, перепись SASS
```

В каждой папке кандидата:

```
ISSUE_TITLE.txt  ISSUE_BODY.md    что уходит первым — правило «сначала Issue»
PR_TITLE.txt     PR_BODY.md       что уходит после его подтверждения
COMMIT_MSG.txt                    тело коммита, ставится через git commit --amend -F
branch.bundle                     ветка от origin/master, git fetch <bundle> <branch>:<branch>
make_pr.py                        стадии: check -> issue -> bundle -> fetch -> push -> create
data/                             сырые CSV, логи, nsys-сводки — всё, из чего собраны таблицы
REVIEW.md                         что нашли независимые ревьюеры и что с этим сделали
```

## Порядок подачи

1. `python make_pr.py check` — проверяет тексты, ничего не трогает.
2. `python make_pr.py issue --yes` — открывает Issue. **Дальше ждём его ответа.**
3. После подтверждения: `bundle --yes` → `fetch --yes` → `push --yes` → `create --yes`.

`bundle` тянет ветку с 5090 по ssh; если сервера уже нет, ветку можно поднять из `branch.bundle`
в папке кандидата: `git fetch ./branch.bundle <branch>:<branch>`.
